# 模式：修订（Revise）

按明确指令修改既有合同。核心原则：**只改该改的，其余一字不动；每处改动
可追溯；改动引起的连锁反应全部处理。**

## 流程

### 1. 基线确认

- 以用户当前保存的文件为基线，不恢复历史版本、不与旧稿比较（除非用户
  明确要求对比）；
- 含修订/批注的 DOCX，先用 `scripts/word_reader.py analyze` 读取原文、接受视图、
  标记视图、时间线、批注线程和条款变化链（见 [Word 深读](word-deep-read.md)）；
  未读完这些视图前不开始改写，也不自动接受/拒绝历史修订；
- 全文 `extract`，通读；属于合同族的，同时提取存在接口的关联文件；
- 确认改动权限与输出方式：清洁稿、未接受红线稿或仅批注稿；红线/批注只另存副本，
  先检查已有修订，禁止自动接受历史变更。普通清洁稿是否改写原件（自动备份）或另存；是否允许
  顺帯修正发现的明显错误（默认不允许，只报告）。PPTX 只能另存精修稿，没有可接受的修订痕迹，
  必须用计划预演并明确告知用户“这是无修订标记的内容修改”。

### 2. 变更影响面分析（动笔前）

对每一项修改指令，先回答四个问题，形成简短的修订方案：

1. **直接落点**：改哪几个文件、哪几条？
2. **术语连锁**：改动是否触碰定义条款/简称？全文（含关联文件）该术语的
   每一处都要同步；用 `search` 全文件扫描确认无遗漏。
3. **引用连锁**：条号增删会导致"见第×条""附件×"等交叉引用错位——增删
   条款后必须全文核对引用编号。
4. **族内联动**：该条款在关联合同中有对应/镜像条款吗（背靠背责任、验收
   矩阵、变更规则、付款条件、SLA）？联动文件一并修订或列入提示。

与项目规则冲突的指令（如要求恢复已否决结构、删除红线条款）：**不执行**，
向用户说明冲突点与依据，请其定夺。

### 3. 实施

红线/留痕/批注使用 [docx-redline](docx-redline.md) 的 inspect → plan（dry-run）→ apply → verify，
不把普通 replace/set 生成的清洁文本当作红线。批注绑定改动理由与 R/C-ID，遇复杂目标停止。

已确认的普通清洁稿使用 `docx_tool.py`（见 [docx-workflow](docx-workflow.md)）：

- 措辞/数值替换：`replace`（多段落命中时必须用 `--para` 逐点确认，谨慎
  使用 `--all`）；
- 整款重写：`set`；
- 新增条款：`insert-after`（克隆同类条款段落以保持格式），条号手工顺延
  并核对后续引用；
- 删除条款：`delete`，删除后核对引用；
- 表格：`add-row` 增行，改单元格用 `set` 对单元格内段落操作；
- 多处改动优先 `batch` + `--dry-run` 预演，确认无误再 `--in-place`。

PPTX 使用 [Office 精修与无头预览](office-workflow.md)：

1. `office_kit.py inspect` 取 SHA、页码和 `shape_id`；
2. 一份计划覆盖全部改动，`pptx apply --dry-run` 验证；
3. 用户确认后 `--commit` 原子另存，工具重新打开并核对未指向内容不变；
4. `pptx verify` 独立复核；
5. 全批文件统一 `render`，查看联系表和异常页原图。

不得用 XML 直接拼接或截图重做来冒充 PowerPoint 修订；不支持复制/删除幻灯片、
SmartArt/图表内部编辑，遇到时缩小范围或明确告知用户改走模板重建。

每处改完即时记录变更日志。

### 4. 修订后全篇扫描

- 重新 `extract`，逐处核对变更点；
- 术语一致性扫描：旧词是否还有残留（`search` 旧术语，应为 0 命中或仅剩
  有意保留处）；
- 交叉引用核对：条号、附件号、合同号；
- 数字复算：被改动的金额/比例/期限与全文其他数字仍勾稽；
- `verify` 校验文件结构；PPTX 用 `pptx verify` 并检查计划结果中的后置条件。
- Office 文件统一无头渲染，检查中文、溢出、重叠、分页和页眉页脚。

### 5. 交付

- 变更日志（[模板](../assets/change-log-template.md)）：位置、原文、新文、
  理由与依据、影响面；PPTX 附计划、执行结果 JSON 和渲染清单；
- 未按指令修改但发现的疑点和隐患，单列"顺带发现"一节，**只报告不擅改**；
- 说明备份文件位置。

## 红线

- 修订不改变商业实质，除非指令本身就是改变实质且不与项目规则冲突；
- 不夹带：指令外的"顺手优化"一律禁止（那是完善模式的事，且需另行授权）；
- 保持体例：编号层级、简称、标点风格与原文一致（体例统一是润色模式的事）；
- docx 原件必留备份；改动后可正常打开（`verify` + `textutil`（macOS）或 `office_kit.py inspect`（Windows）验证）。
- Office 精修不得原地覆盖；PPTX 计划必须绑定源文件 SHA，提交后重新打开验证。
