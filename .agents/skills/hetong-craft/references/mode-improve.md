# 模式：完善（Improve）

找缺口并补强。**先诊断、再提案、经批准、后落笔。** 与审核模式的区别：
审核只出诊断报告；完善要开到处方并在批准后实施。

## 流程

### 1. 缺口诊断（只读）

在审核模式诊断框架（见 [mode-review](mode-review.md)）基础上，聚焦三类缺口：

**A. 条款完整性缺口** — 对照 [审查总清单](checklist-review.md) 条款维度，
找出"应该有而没有"的条款。高频缺失项：通知与送达、合同解除与退出善后、
证据链与单据要求、附件清单与效力顺位、法律适用、反商业贿赂、数据安全。

**B. 风险分配缺口** — 已有条款但分配失衡或断链：
- 责任无上限或有上限无例外（故意/重大过失/人身伤害通常不得限责）；
- 免责条款过宽，掏空主要义务；
- 上下游责任传导断裂（对客承诺了，上游合同没有背靠背接住）；
- 违约后果与义务不配套（有义务无违约后果＝不可执行）；
- 验收/僵局无兜底（对方不验收、不答复时怎么办）。

**C. 可执行性缺口** — 写了但做不到、考不了：
- 义务无量化标准、无期限、无验收方法（"及时""合格""满意"）；
- SLA 无测量方法、无数据来源、无违约计算；
- 付款条件依赖无法控制的事实且无兜底到期日；
- 程序条款无法运转（变更谁提、谁批、多久内批）。

### 2. 完善建议清单（提案）

每个缺口一条提案，格式：

| 字段 | 说明 |
|---|---|
| 位置 | 拟落入的合同与条款位置 |
| 缺口 | 现状与风险（发生了什么会怎样） |
| 建议文本 | 可直接采用的完整条款文字 |
| 依据 | 法律依据/交易惯例/项目规则/关联合同镜像条款 |
| 影响面 | 是否牵动关联文件、是否改变商业实质、税率/定价影响 |

提案分级：**必补**（不补则合同无法闭环或违反强制规定）、**应补**（实质
风险敞口）、**可补**（优化性）。交用户取舍；涉及商业实质变化（价格机制、
责任上限数值、管辖）的，必须由用户明确拍板。

### 3. 经批准后实施

- 用户要求红线/批注时走 [docx-redline](docx-redline.md)，仅另存副本；段落内补强可用受限红线引擎。
  新增整段、表格行等尚不支持的留痕操作应停止并列入人工处理，不退回无痕插入假装完成。
- 对已授权的普通清洁稿，落入方式：新增条款用 `insert-after` 克隆同段格式；新增章节注意条号
  顺延与交叉引用更新；表格补内容用 `add-row`/`set`；
- 族内联动的补强（如对客合同补了 SLA，上游要背靠背接住）必须同步落笔，
  并在交付中说明联动关系；
- 全程记录变更日志（[模板](../assets/change-log-template.md)），理由栏
  引用对应提案编号。

### 4. 闭环验证

- 补强后的条款与既有条款无冲突（特别检查：一般条款与特别条款的效力
  顺位、兜底条款是否吞掉了特别约定）；
- 数字复算、引用核对、`verify`；
- 交付：建议清单（含采纳/未采纳状态）+ 变更日志 + 残余风险提示。

## 红线

- 不以"完善"名义改写商业条款实质（价格、比例、责任分配）——那是用户的
  商业决策，只能提案；
- 不引入项目规则禁止的结构；
- 补进去的条款必须与本合同其他条款啮合，不生造孤立条款；
- 建议文本必须是可直接签署的成品文字，不是"建议增加违约责任条款"这种
  方向性废话。
