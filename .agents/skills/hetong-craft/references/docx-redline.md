# Word 合同红线稿与批注

生成编辑计划前按[新增批注触发标准](comment-policy.md)筛选：原文无须改动的固定条款命中不产生批注；本轮真实修改、问题和笔误仍需按授权说明。

用于用户明确要求“留痕修改、修订模式、红线稿、在 Word/WPS 批注”的场景。本能力在本仓库内独立实现，供 Pi/PiDeck、Claude Code、Codex、DSH 共用，不依赖在线上传。只处理 `.docx`；旧 `.doc`、原生 `.wps` 先经用户确认转换为新的 `.docx` 基线，转换不是无损保证。

真实合同先完成[受理工具](host-intake.md)。开场问答属于受理层，不由XML红线引擎或模型临时拼问卷。后续`apply`附加`--intake-state 本次受理回执.json`，引擎在写入前核对明确提交、源文件SHA及只审/批注/修订权限；回执不匹配则不产生Word输出。该检查不把类别选择解释为商业条件确认，也不替代既有plan/verify。

已调用[XQY双文件专用分支](../../hetong-fast-xqy-v1/references/paired-delivery.md)时，按该分支已授权的“报告＋仅批注副本”范围执行：`build_bundle.py`复用本引擎，限定所有操作为comment，并核对指定基线SHA、全部锚点和正文/历史保留；不编造通用类别回执，也不以此取得正文修订权限。普通红线与本页其他任务仍按通用受理闸门。

**开始修改前先读懂已有审阅。** 含修订/批注的基线先运行 `scripts/word_reader.py analyze`，按 [Word 深读](word-deep-read.md) 核对原文、接受视图、标记视图、时间线和批注线程；不得先接受/拒绝历史修订来让编辑变简单，也不得把批注当正文。

随后按[原生审阅显示与配色](native-review-display.md)检查现有显示及客户端能力，只在可安全限定作用域时指定本轮原生颜色。不得通过正文或批注的字色、高亮、底纹、样式修改模拟审阅效果；无法设置或无法验证时保留原生显示，继续本流程并记录限制。

## 一、输出意图和权限

- **红线稿**：真实的未接受插入/删除修订，供审阅者逐项接受/拒绝，不是把文字涂红。
- **批注稿**：只增加风险、待确认事项或修改理由，正文不变；仍是写入文件，须获用户授权并另存。
- **清洁定稿**：不是本工具的输出，不能悄悄接受全部修订或删除他人批注来制作。
- 纯审核仍只读。用户明确要求把审核意见加到副本中，可生成批注稿；未确认诊断不得顺带生成实质红线修改。涉及新商业方案，沿用 hetong-review 的 R/Q/C 确认闸门。

先确认基线、输出形式、作者显示名称、改动范围及已有修订如何处理。作者使用真实授权身份或“合同审阅”，不冒充律师或对方人员。

## 二、安全边界

工具为 `../scripts/hetong_redline.py`，Python 3.9+ 标准库。所有命令以本文件目录解析绝对路径。它采用“检查 → 编辑计划 → 另存 → 验证”，不支持原地覆盖。

首版覆盖普通正文和普通表格单元格中单个段落的文字改写、插入/删除文字与传统范围批注；未变文字和字符样式尽量原位保留，新增文本继承落点样式。不同语义的字体选择仍须视觉复核。

**不强行处理**：跨段合并/拆分、整行表格增删、格式修订、字段、超链接、内容控件、书签、图片/公式、文本框、目标段内已有修订等复杂结构。已有修订位于别段时保留并续号；目标重叠时停止，不先接受旧修订来绕过限制。宏、签名、保护、Strict OOXML、`commentsExtensible` 新式批注线程等不受支持时，以检查结果为准并停止写入，不删除相关部件。

**既有批注锚点的处理边界**：

- 段落内的既有批注锚点（`commentRangeStart`/`commentRangeEnd`/纯 `commentReference` run）若整体位于文本 run 的一侧（如 Word 常见的零宽段末锚），允许改写该段正文；锚点节点原位保留、不移动、不重建，锚点数量与所在段落由 verify 单独核对。
- 锚点夹在文本 run 之间（含包住整句的常规范围锚）仍按 `interleaved_comment_anchor` 拒绝，避免改写与既有批注选区相交。
- `w:lastRenderedPageBreak` 只是客户端排版提示、不含文字，允许出现在可编辑 run 内；该 run 被拆分改写时提示会丢弃，由 Word/WPS 重新分页，不影响正文与锚点。

**现代批注部件**：文档带 `commentsExtended.xml`、`commentsIds.xml`、`people.xml`（现代 Word 默认保存）时，可以向 `comments.xml` 追加传统批注，并同步补写 `commentEx`（`done="0"`）、`durableId` 与 `people` 记录。既有条目按原字节保留、不重排；相关部件列入允许变更清单，并由 verify 核对既有 `paraId` 不减少、新批注条目齐备、`durableId` 唯一。遇到 `commentsExtensible.xml` 仍整体拒绝。

显式隐藏文字（vanish/specVanish/webHidden 开启）不作为普通可编辑正文。样式继承、主题颜色或白字造成的视觉隐藏不能仅凭文字提取排除，须检查警告并人工复核，不能宣称 inspect 就是屏幕可见全文。

新工具编号为 **RL0001…**，来自自身检查结果；不得与 `docx_tool.py` 的 P/T 编号混用。原文件任何变化后重新检查并生成计划。

遇上述不支持结构或需派生清洁版时，按 [工具边界与替代路径](word-operation-paths.md) 评估其他可靠路径；本引擎的拒绝边界保持不变。

## 三、编辑粒度：保留语义骨架，不追求机械最小字数

1. 一个操作对应一个清楚的审阅意图，必须有条款位置和原因，尽量对应 R-ID/C-ID；一条批注可以解释该操作产生的多处短语修订。
2. 不变文字留在原处，相关的小改合并成可读短语；金额、带分隔符的数值、小数、百分比整体改，不能只把 `600` 中的 `6` 改成 `5`。
3. 同一段的多项改动先合成为一个旧片段与目标片段，由工具分解，不顺序叠加一串互相影响的 replace。
4. 纯新增长条款可能天然超过短语长度；不能为了“粒度分数”删掉必要限定词。超阈值时回看是否可以保留骨架；确须大改，取得确认并在 `broad_reason` 说明原因。
5. 粒度指标是报警器，不是法律标准。批注数量按合同长度和风险密度判断，不套用整份合同最多15条之类硬上限；同根因可合并理由，但所有受影响位置仍要可追溯。
6. 不以“优化措辞”名义修改已确认的完整性、收到、起算点、责任例外、比例与期限。改写前后仍须进行合同语义核对。

## 四、操作步骤

```bash
CRAFT=<hetong-craft技能目录>
R="$CRAFT/scripts/hetong_redline.py"
python3 "$R" inspect 基线.docx > 基线检查.json
python3 "$R" plan 基线.docx edits.json -o 编辑计划.json
# 人工核对命中条款、原文、新文、作者、批注、粒度警告和大改理由后，再执行：
python3 "$R" apply 基线.docx 编辑计划.json -o 合同_红线稿.docx --author "合同审阅"
python3 "$R" verify 基线.docx 合同_红线稿.docx 编辑计划.json > 验证结果.json
```

`plan` 即本流程的 dry-run：只写计划，不写合同。目标文件、计划不得覆盖基线或已有成果；计划被改动或原件哈希变化时重新规划，不手工补 hash 绕过校验。

编辑清单示意（RL 编号必须来自实际 inspect）：

```json
[
  {"id":"C-001/R-001","para":"RL0002","old":"价款为600元。","new":"价款为550元。","reason":"已确认按Q-001调整价款；请同步核对价税与付款节点。"},
  {"id":"R-002","para":"RL0004","old":"收到资料后开始验收","comment":"需确认资料是否完整及送达证据，当前不改正文。"}
]
```

上例数字仅用于说明工具格式，不可用于真实合同。空锚、同段重复命中、多操作落到同一段、目标含复杂结构等均应停止；通过扩大精确原文或重新合成单段目标解决，不使用跳过失败或全局强替换。

## 五、批注写法

复杂批注、跨条款解释及精确选区另见[批注质量与锚定](comment-workflow.md)。

批注写清“编号＋发现/依据＋改动理由或待确认问题”，保持短而可决策：

- 已确认修改：`C-003 / R-007：按Q-002保留隐蔽瑕疵救济，避免验收视为全面弃权。`
- 待确认：`R-009：正文未明确付款起算资料，建议双方确认完整提交及接收凭证；本处仅批注。`

不把假设事实、未核法律或未获用户确认的方案写成确定结论；不在批注中泄露内部谈判底线、账户或个人敏感信息。给对方的外发版与内部审核稿须区分，删除内部意见不能靠自动“清理全部批注”。

## 六、验证与交付

机器验证须证明：

1. 原件 SHA256 不变，新增文件不覆盖旧文件；ZIP/XML 可解析，相关部件注册与批注锚点闭环。
2. 本轮修订为真实 ins/del，删除用 delText；作者、时间、ID正确，旧批注和修订保留。
3. **仅拒绝本轮新增修订**后回到基线，**仅接受本轮新增修订**后等于按确认清单独立计算的目标。历史修订保持未处理，不能用“接受全文”冒充本轮验证。
4. 未修改部件字节不变；已改段的原字符样式在拒绝视图中一致。另从源件和授权计划重建期望输出，逐成员核对解压内容，防止结果额外注入域、节属性变更、重复旧ID或新增关系。该重建核对不能替代独立的语义和视觉复核。
5. 程序验证不等于 Word/WPS 实机兼容。对可用本机应用，用虚构样例测试打开、修订/批注显示、接受/拒绝及另存往返；真实合同不得未经授权送往云转换。不同版本客户端须按实际结果披露。

`verify` 对应的是本工具直接生成的那个版本。Word/WPS 另存可能重排XML，甚至接受/拒绝部分修订；此时旧计划校验失败不当然表示文件损坏，也不能忽略失败继续声称通过。按新版本重新建立基线，走版本对比/关闭核验，不复用旧计划追写。

需要额外核对成品是否保留历史修订/批注、是否只有本次新增内容时，运行只读审计器（需要明确的修改前基线）：

```bash
python3 ../scripts/audit_docx_review.py 合同_红线稿.docx --before 基线.docx --author '本次署名' --out 验证结果/审阅结构审计.json
# 仅批注、未改正文时加 --comments-only
```

审计器的短/长候选、选区跨段等只是人工复核线索；它不替代 Word 接受/拒绝、语义粒度、法律判断和页面视觉检查。

交付：未接受红线/批注副本、编辑计划、变更日志及验证结果。告知在 Word/WPS 的“审阅 → 显示标记 → 所有标记”查看；不要承诺所有客户端默认打开即显示。签署定稿必须另经用户确认处理修订和批注，不把红线稿当已签署文本。

如执行配色检查，在现有验证记录中注明原生颜色已设置并验证、保留原生显示或未验证；不以文件内颜色值证明客户端高亮，也不保证颜色随文件跨电脑保持。
