# 模式：润色（Polish）

只动语言，不动实质。判定基准：[语言体例规范](style-zh-hetong.md)。

**黄金标准：润色前后，任何一方的权利义务、金额、期限、责任范围发生的变化
必须为零。** 凡会改变法律效果的"润色"，都不是润色——归入修订/完善，另行
授权后处理。

## 润色的合法范围

| 可以做 | 不可以做 |
|---|---|
| 错别字、漏字、衍字 | 改变金额、比例、期限、税率 |
| 术语统一（同一概念全文同一词） | 增删义务、责任、权利 |
| 语法与语序（消除歧义结构） | 改变履行顺序、条件、主体 |
| 标点全角化、格式统一 | 改动定义条款的语义边界 |
| 编号体例统一（不改动条号映射关系） | "优化"管辖、违约、免责表述 |
| 删除无意义的重复修饰 | 合并/拆分条款（影响引用） |

拿不准某处是否"纯语言"时：列入疑问清单请用户定夺，不擅自改。

## 流程

1. **基线与快照**：`extract` 全文存档（作为润色前后逐段 diff 的基准）。
2. **问题清单**：按 [语言体例规范](style-zh-hetong.md) 逐项扫描，
   用 `search` 取证（如某术语的全部出现位置），形成"问题 → 位置 →
   建议改法"清单。高影响改动（术语替换波及多份文件、定义项更名）先给
   用户过目确认，再实施。
3. **实施**：要求留痕/批注时走 [docx-redline](docx-redline.md)，保留未接受修订并另存；
   普通清洁基线才用 `replace`/`set`/`batch --dry-run` → 确认 → 另存或已授权的 `--in-place`。
   术语替换必须逐命中点确认语境（同一词语在不同语境可能指不同事物，
   不能无脑全局替换）。
4. **零实质变化验证**：
   - 润色前后两份提取文本做结构化对比：段落数、条号序列、全部数字
     （`search --numbers` 结果逐条比对）完全一致；
   - 变更日志逐条注明"仅语言，无实质变化"及判断依据。
5. **交付**：变更日志 + 未决疑问清单（发现的实质问题只报告，转完善/修订）。

## 常见陷阱

- **术语替换波及关联文件**：如把 A 合同中的"运维服务"改为"运行保障"，
  B、C 合同及三方文件中的引用必须同步，否则合同族内部术语断裂。
- **修饰语有法律意义**："重大""合理""及时""书面""当场"等限定词不是
  冗余，删除即改变义务强度。
- **顿号/逗号改变列举范围**："A、B 和 C"与"A，B 和 C"结构不同，改标点
  前先确认列举关系。
- **大小写金额、日期、编号**不是"文字"，属于实质信息，润色不得触碰
  （发现不一致时报告）。
