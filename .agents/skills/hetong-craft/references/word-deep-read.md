# Word 合同精细阅读与修改时间线

用于**已有大量修订、批注、回复和多轮修改的 `.docx` 合同**。先重建“文件实际记录了什么”，
再分析“业务逻辑”，最后才形成审核或修订意见。阅读器只读，不改 Word，不自动接受/拒绝修订。

## 一、为什么不能只看 Word 当前屏幕

同一份 Word 可能同时包含：
- 原文、插入文字、删除文字、移出/移入文字；
- 段落标记插入/删除、表格行/单元格插入删除、格式修订；
- 传统批注、现代线程回复、已解决状态、失去锚点的批注；
- 隐藏文字、页眉页脚、脚注尾注、文本框和表格单元格；
- 不同作者、不同系统时钟产生的时间戳。

只读“当前显示版本”会把原文、未接受插入和作者意图混在一起。本流程固定生成三种视图：

| 视图 | 含义 | 用途 |
|---|---|---|
| `original.md` | 拒绝全部修订后的原文 | 看交易最初约定、判断改动方向 |
| `accepted.md` | 接受全部修订后的文本 | 看如果全部接受将形成什么条款 |
| `markup.md` | 原位插入/删除/移入移出和批注编号 | 逐项回看改动，不把标记当最终文本 |

它们都是**阅读分析视图**，不是 Word 当前选择的显示模式，也不是可直接签署的定稿。

## 二、运行

```bash
WR=<hetong-craft技能目录>/scripts/word_reader.py
OUT=<任务产出目录>/word-deep-read
python3 $WR analyze 合同.docx --out "$OUT"
```

常用参数：

```bash
# 含隐藏文字也纳入视图；默认隐藏文字不进入主视图，只在 markup/异常中提示
python3 $WR analyze 合同.docx --out "$OUT" --include-hidden

# 覆盖同目录中本工具已有的产出；不覆盖其他文件
python3 $WR analyze 合同.docx --out "$OUT" --force

# 作者活动时段的分隔阈值，默认 30 分钟；只是推断，不是谈判轮次
python3 $WR analyze 合同.docx --out "$OUT" --session-gap-minutes 45
```

输入文件任一字节变化都会重新计算 SHA；分析后若发现输入改变，拒绝把结果当作同一版本。
原件保持只读。

## 三、输出文件

| 文件 | 内容 |
|---|---|
| `accepted.md` / `original.md` | 接受/拒绝全部修订的阅读视图，带 `WR` 段落定位 |
| `markup.md` | 修订内联标记、批注编号、隐藏文字和表格结构提示 |
| `timeline.csv` | 修订与批注的合并事件时间线，适合表格复核 |
| `comments.csv` | 批注线程、父批注、解决状态、锚定文字 |
| `deep-read.json` | 完整机器可读数据：段落、修订、批注、条款变化链、异常 |
| `deep-read.md` | 事实层摘要、时间线、条款变化、批注、异常和阅读框架 |

ID 约定：

- `WR0001`：段落定位；表格段落带 `T1 R2C3`，页眉页脚等带故事名称。
- `TV0001`：修订事件；`EV0001`：修订与批注合并后的时间线事件。
- `C0001`：批注（按批注正文日期排序后重新编号）；`S0001`：作者活动时段（推断）。
- `H0001`：条款/标题组；不是法律意义上的条款编号，正式定位仍以合同文字和条号为准。

## 四、阅读顺序

### 1. 先看文件事实和覆盖

打开 `deep-read.md` 第一节，确认：
- 文件 SHA、大小、创建/最后修改时间、作者/最后保存者；
- 当前跟踪修改开关；
- 读取了哪些故事（正文、页眉页脚、脚注尾注）；
- 是否有宏、签名、保护、嵌入对象、图片、字段、隐藏文字；
- 是否有修订日期缺失、未来日期、早于创建时间、时区未标明。

### 2. 对照原文与接受视图

按条款顺序读 `original.md` 和 `accepted.md`，不要先读某一轮批注：
1. 原文的权利义务、价款/税、交付/验收、付款、质保、责任、解除、争议解决；
2. 接受后的同一组条款；
3. 逐条记录“文字发生了什么变化”，先不做“谁有理”的判断。

对每处差异标记：增加/删除/移动/格式、涉及数字/期限/主体/责任/条件、是否有批注解释。
用 `markup.md` 和 `timeline.csv` 回查精确修订，不能只凭两段文字猜。

### 3. 重建修改时间线

时间线分两层：

1. **记录层**：`timeline.csv` 的原始 `date_raw`、作者、修订类型、条款、文本摘要；
2. **推断层**：`S0001` 等作者活动时段，按同一作者相邻事件间隔推断，**不是**“第一轮谈判/
   第二轮谈判”。不得把推断时段写成双方事实。

处理规则：
- 时间戳优先按文件原值展示，不擅自把无时区值转换成北京时间；
- 无日期修订排在最后并提示，不强行补日期；
- 未来日期、早于文档创建、晚于最后修改的日期均列入异常；
- 同一作者、同一分钟的多条修订按文件顺序排列，不宣称存在更细的因果顺序；
- 事件之间的“先评论后修改”只能说明文件记录顺序，不能证明作者看到了批注或同意其内容。

### 4. 重建批注线程

看 `comments.csv` 或 `deep-read.md` 第五节：
- 根批注、回复、父批注关系；
- `已解决 / 未解决 / 状态未知`：现代 `commentsExtended` 的 `done` 才能作为解决状态；
  旧式批注没有该字段时只能是“状态未知”，不能当作未解决或已解决；
- 批注锚定的接受视图文字、原文文字；锚点是否被删除；
- 有锚点但没有批注正文、有批注正文但没有锚点、回复没有独立锚点（正常）等区别；
- 批注意见是否与正文实际修订一致：批注说“已修改”不等于正文真的改对。

### 5. 按条款重建业务变化链

`deep-read.json` 的 `clauses` 和 `deep-read.md` 第四节提供：
- 原文、接受文本；
- 修订 ID/批注 ID；
- 变更片段和关键词信号（金额、付款、验收、期限、责任、解除、知识产权、保密、质保、
  管辖等）；
- 作者和时间范围。

关键词只是**检索提示**，不代替业务判断。逐条回答：

1. 交易骨架是否变化：当事人、标的、价款/税、交付、验收、付款、质保、责任、退出、
   争议解决？
2. 风险是否迁移：谁承担延迟、质量、付款、验收、第三方、数据/IP、不可抗力、解除后的
   责任？是否出现责任上限、免责、期限缩短或证据门槛？
3. 对价是否联动：数量/范围/税率/发票/付款节点/质保金是否随价款或责任改变？
4. 义务是否可履行：新增义务有没有主体、行为、期限、标准和违反后果？
5. 是否有“文字变了但机制没变”或“机制变了但文字没改”的条款？
6. 是否有已删除的旧条款仍被其他条款引用？
7. 批注提出的问题是否已在正文解决，还是只留下口头/批注承诺？
8. 是否存在同一问题被多个作者反复改写、回退或净额为零的情况？

### 6. 形成分层结论

报告必须把三层分开：

- **文件事实**：OOXML 中确有/确无的文字、修订、批注、时间、锚点；
- **阅读推断**：从改动方向推测的商业目的、谈判阶段、作者意图；
- **法律评价**：结合现行法和交易背景作出的效力、风险、可执行性判断。

没有交易背景、授权或用户确认时，不得把“某个作者删除了责任上限”写成“双方已同意删除”，
也不得把批注中的建议当成合同条款。业务上不利不等于法律无效。

## 五、报告中必须保留的证据

每条重要结论至少对应：
- `WR` 段落/条款位置；
- `TV` 修订或 `C` 批注编号；
- 原文片段和接受后片段；
- 时间（原始值）和作者；
- 若有时效/法律判断，另列法律来源核验（按 `hetong-review` 的 S-ID 规则）。

报告末尾列“未决问题和证据缺口”：批注状态未知、锚点丢失、修订无日期、表格结构变化、
嵌入对象、隐藏文字、字段、自动编号和复杂布局等。

## 六、与其他流程的衔接

- **审核**：先做本深读，再进入 `hetong-review` 的全文扫描；`findings` 可引用 `WR/TV/C`，
  但仍须用条款文字和法律来源独立复核。
- **修订/红线**：先保留原始审阅记录和深读结果，再生成新红线稿；不得先“接受全部修订”
  来简化编辑，也不得清理历史批注后冒充原稿。
- **关闭核验**：把原审核 R-ID、深读时间线、实际修订和变更日志逐项对应，不能以“已修改”
  替代“已修复”。
- **版本对比**：这里比较的是同一文件内部的修订历史；跨文件/跨版本对照仍走合同族对比流程。

## 七、边界

- 读取的是 OOXML 文本与结构，不执行宏、不渲染图片、不做 OCR，不解析嵌入对象内部。
- 自动编号、域计算结果、复杂表格布局、文本框位置和最终分页以 Word/WPS 客户端为准；
  阅读视图会保留可见文本和结构警告，但不保证与屏幕像素完全一致。
- 隐藏文字检测覆盖直接 `w:rPr`、文档默认字体、段落样式和字符样式链；表格样式、编号
  样式和主题颜色造成的视觉隐藏不能保证全部展开，仍须结合 `markup.md` 和 Word 屏幕复核。
- 现代批注线程、回复和解决状态能读取则读取；旧式批注没有解决字段时标为“状态未知”。
- 文档有编辑保护、签名、宏或 Strict OOXML 时仍可只读分析，但不会移除保护；交付报告须
  同时披露这些限制。
- `accepted.md` / `original.md` 是分析视图，不是签署稿。正式定稿必须另行处理修订和批注，
  并由用户确认。
