# 两版近似合同与未留痕改动

用于用户同时提供**前后两版近似 DOCX**，要求在正常对比审核之外检查“暗改”：有些文字没有通过 Word 修订渠道，而是直接改在正文、表格、页眉页脚或隐藏文字里。

本功能由 `hetong-craft` 统一提供，作为近似合同的版本核对补充，不替代 `hetong-review` 的条款对比、法律审查和商业判断，也不自动修改任何合同。

## 一、检测口径

对后一版分别构造两个文本基线：

1. **后一版拒绝全部修订**：Word 中如果把后一版所有历史修订都拒绝，剩下的原始文字；
2. **后一版接受全部修订**：Word 中如果把后一版修订都接受，最终可见文字。

再与前一版的基线视图比较：

| 比较 | 含义 |
|---|---|
| 前一版基线 vs 后一版**拒绝全部修订** | 后一版修订记录**不能解释**的文字差异，即未留痕改动 |
| 后一版拒绝全部修订 vs 后一版接受全部修订 | 后一版修订记录**可以解释**的改动 |
| 前一版基线 vs 后一版接受全部修订 | 两版最终可见文字的总差异 |

默认以前一版的**接受全部修订**视图作为基线；也可用 `--baseline-view original` 改以前一版的原文为基线。若前一版自身还有未接受修订，必须在报告中说明所选基线，不能把两种基线混用。

同时检查：

- 前一版已有修订/批注在后一版是否消失；
- 后一版跟踪修改开关是否被关闭；
- 隐藏文字是否变化；
- 图片、嵌入对象、图表等媒体部件是否变化；
- 两版可见文本相似度是否过低，是否可能并非同一合同族。

## 二、运行

```bash
python3 hetong-craft/scripts/hidden_change.py compare \
  --before 原件/合同_v1.docx \
  --after 对方返回/合同_v2.docx \
  --out 产出/暗改检测
```

可选参数：

```bash
--baseline-view original     # 以前一版拒绝修订的原文为基线
--include-hidden             # 隐藏文字纳入主视图；仍会单独报告隐藏文字变化
--similarity-threshold 0.6   # 低相似度提示阈值，默认 0.55
--force                      # 覆盖本工具已有的三个输出文件
```

工具只读输入，不修改原件，不自动接受/拒绝修订。输出冲突时默认拒绝覆盖。

## 三、输出

| 文件 | 内容 |
|---|---|
| `hidden-change-report.md` | 给人看的结论、未留痕改动、历史/非文本变化和局限 |
| `hidden-change.json` | 完整机器可读结果、findings、三组差异 |
| `content-diff.csv` | 未留痕/留痕/总差异的逐条对照 |

finding 使用 `HC-001` 稳定编号，至少包含类别、等级、位置、前文、后文、证据、建议和置信度。

## 四、结果解读

### 1. 未留痕文字改动（重点）

`HC` 中的 `untracked_text_change` 表示：后一版拒绝全部修订后的文字仍与前一版基线不同。常见原因：

- 直接在正文/表格中改字，没有开启修订；
- 先接受旧修订，再直接修改；
- 从其他文件复制粘贴覆盖正文；
- 删除后重新输入，但没有留下删除/插入记录；
- 把修订记录清除后再改文。

这不等于已经证明有人恶意改合同。必须先核对：是谁返回的版本、是否说明过修改、是否有邮件/微信/会议纪要、是否经过授权、是否是排版/转换造成。

### 2. 可由修订记录解释的改动

`tracked_text_changes` 只说明后一版修订记录能解释这些差异，**不说明修改内容正确或已经我方同意**。仍要按正常审核核对金额、期限、责任、附件和联动条款。

### 3. 审阅历史减少

前一版有修订/批注、后一版没有或明显减少，可能因为：

- 正常接受了修订并生成清洁版；
- 删除/解决了批注；
- 清除了修订历史，或者把文件“另存为”时丢掉了审阅记录。

报告只把它列为待核对事项；不得仅凭“历史减少”指控暗改。

### 4. 非文本变化

图片、嵌入对象、图表、隐藏文字的变化不能由文字修订解释，应单独核对：

- 图片是否被替换、裁切或覆盖；
- 嵌入的报价单/技术附件是否被替换；
- 隐藏文字是否包含未公开承诺或旧底价；
- 页眉页脚、脚注是否被改。

### 5. 低相似度

若两版相似度低于阈值，可能不是同一合同族，或者版本关系判断错误。此时先确认文件关系，不要把差异直接作为暗改证据。

## 五、误报与局限

- 文本比较按正文、表格、文本框分组；表格行号移动、复杂域、自动编号、列表编号、页面布局和图片内文字可能导致误报/漏报。
- 只比较 `.docx`；PDF 扫描件、旧 `.doc`、`.wps`、加密文件不适用，需先转换并核对转换差异。
- 不执行 OCR，不读取图片内文字，不解析嵌入对象内部。
- 不比较完整字符格式和版式；格式变化、页边距、字体替换需在 Word/WPS 中另行核对。
- 未提供前一版、两版不是同族、或前一版基线选错时，工具可能产生大量伪差异。
- 输出只是证据线索，不是对作者主观故意的认定，也不替代法律意见。

## 六、建议的处理顺序

1. 先确认两版文件名称、来源、时间和传输路径；记录双方 SHA-256。
2. 运行本工具，先看“未留痕文字改动”和“低相似度”。
3. 对每条 `HC` 项回看原文、表格、附件和修订/批注，不只看摘录。
4. 再按正常流程做条款、金额、法律和商业审核。
5. 向对方发问时使用“请说明该处未留痕修改的依据/时间/授权”，不要直接写“你们恶意修改”。
6. 若对方无法解释，保留原件、检测结果和沟通记录；需要重签或补充确认的，另行走修订/确认流程。

## 七、与正常对比审核的衔接

- 本工具只回答“后一版是否有修订记录解释不了的文字变化”；
- `hetong-review` 的版本对比回答“哪一条款发生了实质变化、对谁有利”；
- 两者都完成后，才能形成“是否同意该版本”的结论。
- 不得用本工具的结果替代条款审查，也不得用“有修订记录”替代对修改内容的实质核对。
