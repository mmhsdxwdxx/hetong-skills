# 合同 Word 批注的内容与锚定

> 本文件是 `hetong-server` 专用批注质量标准；真实批注写入使用 `../../hetong-craft/scripts/hetong_redline.py`，审阅历史先读 `word_reader.py`。

在用户要求合同批注或修订批注版时读取。这里只规定合同批注的质量和验收；实际 Word 工具选用当前环境可用的 DOCX 能力。批注必须是 Word 原生批注，不能用正文括号、红字或报告脚注代替。

## 一个问题应如何写清楚

先反查全文、附件和例外，确定问题确实成立。按读者下一步要做的事组织批注，通常用一个短标题接一段自然文字；复杂的公式或跨条款关系可分两三段。不要强制每条都有固定栏目、字数或风险标签。

批注应让读者不打开外部报告也能理解：

1. **对象与机制**：哪一句、哪两个条件或数值存在什么具体问题，在什么场景下影响谁。不要仅写“有风险”“表述不清”。
2. **处理与理由**：已经怎样局部修订，为什么；涉及底线时解释其内容，不能只写“根据B09”。未修正文时明确这是建议、商业选择还是待核实事实。
3. **边界与下一步**：已有条款解决了什么、哪些保护应保留；尚缺哪项事实，由交易双方、供应商或银行确认什么。确无未决事项时不机械追加“请确认”。

优先把与该问题有关的关键事实写进去：比例的计算基数、单位、公式、期限起点、例外条件、同步条款号。数值未填则给符号公式和成立条件，不编金额。只有法律或产品资料实际支撑本条判断时才附已核验的官方依据、日期和可读链接；不得复用旧任务链接来宣称本次已核验。

使用准确的处理状态：

- **已修订**：所述修订确实存在于交付文件；说明修复的机制及保留的保护。
- **待确认/待核实**：写清缺少的具体事实或决策及不确定性，不把未知写成违约或违法，不擅自填交期、税负、测试阈值或供应商承诺。
- **建议协商/保留提示**：说明商业影响和可选处理，不把谈判偏好说成硬错误。已有保护充分时撤回缺陷；只有仍值得处理的剩余影响才保留提示。

同一批注可以包含“已修订＋仍待确认”，但要明确哪部分完成、哪部分未完成。不把已撤回问题、过去版本过程、对模型的指令写进对外批注。

## 批注粒度与修订粒度分开决定

**修订单位是可接受或拒绝的一次语义改动；批注单位是读者可理解并处理的一个问题。** 两者并非一一对应。

- 同一原因引起正文、公式、附件多处同步修改：主要条款放一条完整批注，点名联动条款；只有远处确需提示或另有行动人时增加简短交叉提示，不复制整段解释。
- 同一段落包含两个独立决策，如“退款期限已补齐”和“合法交付资料待核实”：拆为两条，分别锚定相关语句。
- 修正孤立错字或机械同步数字通常不需要独立长批注；涉及责任分配、商业参数或待补信息则说明原因。不存在固定批注数量或一条基线一条批注的配额。
- 详细度来自机制、计算、边界和可执行下一步，不来自重复原文、堆砌法条或逐项声明“未改什么”。

## 最小充分锚点

先拟定批注要解释的原文，再选择锚点。优先覆盖有问题的完整短语、分句或句子；覆盖整段只在批注确实针对该段整体时适用。

- 不只选一个孤立的“3%”“期限”或句号而让读者猜对象；独立金额字段本身就是问题时，可连同字段名称、计算基数选择。
- 跨条款冲突锚在主要处理条款，在批注内准确指出另一条；不拉一个横跨数页、包含无关条款的大范围。
- 空白主体、空金额、缺机制：锚在最近的字段标签、表格单元格或承接条款，明确应补位置，不挂在文首标题或任意空段落。
- 图片配置附件：先看图片，再锚在图片所在段落、相邻标题或相应正文，说明具体参数。**识别出的图片文字不是 DOCX 可选择文本**：写入清单须明确“图片/标题锚点”，不得把 OCR 得到的整句当作可搜索的 run 选区。图片锚点可能没有文字，应回看页面而不是判为丢失。
- 锚点与新增/删除修订重叠时，选择能在 Word 中稳定定位的语义范围，保持合法结构；必要时覆盖整个对应插入单元或相邻保留文字，并核对扩展后是否夹带无关语句。不得为缩短锚点损坏修订结构。
- 同一句多次出现时，结合条款、附件、表格单元格及上下文唯一定位。段落序号、首次字符串命中、仅检查 `comments.xml` 都不能证明挂在正确位置。
- **物理段落不等于语义句子**：原 Word 可能把一句话拆在两个段落或分页处。若提取的选区以“果及……”开头或停在“后续质”等半词处，必须回查相邻段落；选择完整的关键分句，必要时跨相邻段落锚定同一个意思。不能因为脚本选择了“整个段落”就认定粒度合适。

## 三个经过抽象的写法示例

以下只是批注写法，不是新商业默认值或法律结论；交易数字、期限和条款号须按本次原件核对。

**验收起算已协调**（锚在起算条件，而非整条交付机制）：

> 原文要求提前5个工作日通知，却要求收到通知后3个工作日到场，可能在到货前即触发迟延。现以通知已收到、货物已到达且具备约定测试条件均满足为起点，并同步到货通知附件。原有测试时长及合理顺延安排继续适用；现场应记录实际满足条件的时间。

**责任上限与担保同步**（一条批注解释多处联动）：

> 正文约定30%预付款本金加3%履约担保，附件却仍写35%及5%履约比例。本次依据已确认的33%结构，同步附件总额、逐台履约减额和总体责任上限。其他条款中的5%若是具体违约计收方法，仍按其计算基数计收并受总体上限约束，不机械改成3%；本金返还不计入赔偿上限。

**交货排期待确认**（不把可协调解释写成确定冲突）：

> “【总工期】完成”与“每周不少于【批次数量】台”尚未确定首批周次。【合同总台数】按每周【批次数量】台为【批次数】批；具体首批周次、是否增量及每批截止日尚待确认。请据此核对宽限期起算依据；本示例不代填日期。

不合格写法包括“按技能修改”“风险较大请注意”，以及把上述解释复制到每个数字旁边。示例中的反证方法可以复用，交易结论不能直接复用。

## 写入与交付校验

1. 原件另存副本，记录本次新增批注/修订 ID；署名遵循本次指定值，未指定用 SR。保留已有批注、回复、解决状态和修订，不能覆盖整个 `comments.xml`。历史讨论不因更新正文而自动获得删除授权。
2. 检查 comments 部件、关系、Content Type 和锚点/引用 ID 的连接。既有线程式批注或复杂结构须用支持它的工具；不能为适配简单脚本把历史线程扁平化。
3. **从最终 DOCX 重新提取每条新增批注的真实选区、正文和作者，逐条对照审查结论**。检查锚点过宽/过窄、重复解释、状态误写、正文已经修复却仍说“缺失”、公式/引用未同步及待核实事实被写成确定结论。
4. 批注版不改正文时，比对正文、表格、附件及原有修订，确认只有已授权的批注变化；修订批注版另按修订流程验证接受/拒绝结果。保留本次 ID 清单，不依赖作者名筛选本次修订（历史可能同名）。
5. 检查修订显示和接受本次修订后的连续文本及页面。**PDF 渲染通常不能验证批注气泡**；结构校验必须单独做，有 Word 原生界面时再检查选区与气泡显示。不能把渲染成功说成已验证 Word 批注界面。

只读提取与基础检查工具（`<python>` 使用当前环境的文档运行时，`<skill>` 为本 profile 目录）：

```bash
<python> ../../hetong-craft/scripts/audit_docx_review.py final.docx --before source.docx --author 示例署名 --out work/review-audit.json
# 仅批注任务增加 --comments-only；未指定署名时 --author SR。
# 仅批注任务增加 --comments-only；未指定署名时 --author SR。
```

脚本输出摘要，完整批注选区和修订内容写入本地 JSON。错误退出码为1；提示需人工检查，不能直接定为缺陷。短修订可能是合理金额字段，长锚点也可能是完整机制，长度只用于定位候选。工具只检查常规 WordprocessingML 批注及基础历史保留，不修改文件，不证明法律正确、语义粒度适当、完整 OOXML 合法、接受/拒绝可逆或视觉无误。复杂历史结构应补相应验证，不因脚本通过省略上述校验。
