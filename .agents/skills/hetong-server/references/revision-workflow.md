# 获准后的修订与验证

> 本文件是 `hetong-server` 专用修订补充；实际 Word 写入使用 `../../hetong-craft/scripts/hetong_redline.py`，存量审阅先读 `word_reader.py`，权限与留痕仍受 `AGENTS.md` 和 `../../hetong-review/SKILL.md` 约束。

## 执行范围

“按建议修改”覆盖已明确的方案及其必要同步引用、数字和附件改动，不再逐条批准。报告中的互斥选项、底线例外或关键参数待选择时，先完成独立部分，仅询问剩余必要事项；未选择的底线例外不自行写入。

修改前记录原件路径、版本及哈希，保留原件，默认另存修订稿。只改授权文件，保护已有修改、格式、表格、字段、批注和修订。单笔修改不授权更新技能基线、上传或向交易对方发送。

## Word 留痕

使用本仓库的 `../../hetong-craft/scripts/hetong_redline.py`（inspect → plan → apply → verify），只加载修订与验证所需说明。必须生成真实 Word 修订；红字、高亮、普通替换或仅打开修订模式不能证明已有编辑留痕。

本 profile 未指定署名时默认 **SR**；调用 `apply` 必须显式传 `--author SR` 或本次用户署名，不要依赖通用引擎的其他默认值。

此要求适用于工作底稿及修订交付版。用户选择清洁版时，先保留经验证的留痕底稿，再派生清洁副本，不要求清洁副本仍保留修订痕迹。

- 新增用插入修订，删除用删除修订，替换保留原文删除与新文插入。表格、段落及格式变化在适用时也保留真实修订。
- 本次新增修订和批注按用户指定署名，未指定默认 **SR**；覆盖正文、表格、附件及必要格式修订，保留历史修订的原作者与时间。不得改写文档所有历史作者来实现统一署名。
- 不擅自接受、拒绝或清除已有修订与批注。目标与历史修订重叠时先识别原文和当前显示版本，再用支持此情形的方式处理，不重建干净文档丢失历史。
- OOXML 编辑须保护包关系、样式、编号、域及嵌入内容，修订 ID 合法且不冲突；局部修改不重写整份 Word。
- 同步正文、附件、付款比例、担保金额、减额、索赔范围、宽限期引用及生效/失效时间。没有实际保函时不声称改过银行保函。
- 仅有 PDF/扫描件或缺可编辑原件时，可交付已授权替换条款和对照稿，说明无法保留原 Word 修订历史的具体缺口；不能宣称对照稿或 PDF 批注即 Word 修订。

## 先选语义范围，再写修订

在任务工作目录保留简明改动清单，记录问题、基线/用户指令、条款定位、原文选区、替换文字、联动位置和待确认事项。清单服务于执行与验收，不默认交付成另一份冗长报告。

- **金额、比例、日期等独立字段**：改变的是整个字段，如 `5% → 3%`；不要只删 `5`、插 `3`，也不要为该字段替换包含其他义务的整段。若句子只有比例改变，修订选区只取 `5%`，无需替换整句；批注可以选含计算基数的完整分句。逐处判断数字用途，不全局替换所有 `5%`。
- **局部义务或条件**：选择能独立说明变化的短语或分句，包含必要的主语、触发条件和标点。相邻文字共同完成同一意思时合并留痕，不输出连续的单字/标点插删。
- **句子逻辑重组**：整句替换，保留同段中仍有效的前后句。只有整段制度确需重写且各句相互依赖时才整段替换；不能把整段替换作为默认兜底。
- **新增机制**：优先在对应条款增加一个完整句子；确需独立段落时插入段落，不连带重写旧条款。图像附件不得因提取不到文字而判定缺失，未经确认不重绘配置图片或补造技术参数。

程序可以辅助定位和比较，但由语义计划决定修订边界。段落序号只是定位辅助，每次执行前还须核对条款和原文唯一匹配；遇到零命中、多命中或历史修订重叠，停止该处写入并重新定位，不取第一处、不扩大整段来逃避问题。跨 run 修改时保留原有格式、域、超链接和批注锚点；工具不支持该结构就换可靠路径。

后续只调整修订呈现时，**接受本次修订后的目标文本必须与已确认版本相同**。可以从已核对的原始基线重新生成本次修订，但不得丢失用户其后新增的修改、历史批注或修订。后续改参数时同步对应正文、附件及复算记录，不以重建方式恢复已废弃参数。

## 验证与交付

1. 对照已授权发现与适用立场的 B01—B11 或 A01—A04 检查落实，复算受影响数字、时间顺序和引用。
2. 检查文件可读，新增修订真实存在、作者符合本次署名且覆盖变化；历史修订、批注、内容、表格和附件未丢失。按问题检查实际修订范围，而非仅看 XML 节点数量；段落标记、格式修订和文字修订须区分统计。
3. 在临时副本模拟接受本次新增修订并比对目标文本；模拟拒绝本次新增修订并比对修改前文本。只处理本次修订，不能误处理历史修订，不在留痕交付稿中实际接受/拒绝；清洁副本按下节单独生成。
4. 用环境支持的渲染/Word 检视检查页面、表格、编号、修订显示和缺字；结构检查不等于排版验证。无法验证则准确说明缺口，不宣称全部通过。
5. 按开场确认的版本交付：修订批注版、清洁版或两份。附简明改动说明、未决事项及验证范围；未要求清洁版时不额外生成。文件实际生成并检查后再报告完成。

## 清洁版与双版本

- 清洁版是已确认目标正文的无痕副本，不是仅在 Word 中选择“无标记”显示。实际移除批注及相关锚点/关系/扩展部件，按明确选择处理修订；不能只隐藏，或只删除 `comments.xml` 造成悬空引用。
- 原件和留痕底稿保留所有历史修订及批注。若历史修订尚未决定取舍，按 [开场分流](intake-workflow.md) 仅追问这一问题；不得用“接受全部”顺手裁定旧争议。旧批注中的未决业务事项须单独保留在交付说明，清洁副本移除批注不表示事项已经解决。
- 两份从同一底稿生成。应用相同的历史修订决策并接受本次修改后，修订版的目标正文须与清洁版逐段、逐表、含页眉页脚等相关文字比对一致；附件、图像、编号、字段及金额同步核对，不能以总字符数相同代替一致。
- 检查清洁版没有残留的插入/删除/移动/格式修订、批注及悬空关系；文档能正常打开，渲染无异常。双版本各自做页面检查，页数可因修订显示不同，不要求分页完全相同。
- 只交清洁版时不把内部留痕底稿也交付成第三份文件。清洁版不得擅填未决金额或日期，不把“清洁版”命名或表述成“已确认可签署”。

带批注时按 [批注内容与锚定](comment-workflow.md) 逐条回读。可用只读工具 `../../hetong-craft/scripts/audit_docx_review.py` 提取成品锚点与修订清单、检查新增署名和基础连接；它不代替接受/拒绝验证、排版检查、法律判断或粒度审阅。运行方法见批注参考。
