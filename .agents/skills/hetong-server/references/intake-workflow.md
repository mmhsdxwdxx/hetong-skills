# 开场问题与交付分流

> 本文件是 `hetong-server` 专用 profile 的开场补充；通用受理、权限和诊断仍按 `../../hetong-review/SKILL.md` 执行。

用于真实合同任务的开场及版本切换。目的是一次确认影响审查或交付的选择，不是要求用户重新录入合同，也不是每次凑齐六道问答。

## 六类信息及问法

先读取用户本次指令并快速识别材料，再只问表中未明确、适用的项目。优先一次合并呈现；工具限制问题数量时合理分组，不先只问立场、等回答后才逐项追加。

| 信息 | 建议问题和选项 | 何时需要问 |
|---|---|---|
| 1. 我方立场 | **本次代表哪一方？** 甲方／乙方；按合同核对实际主体及买卖角色。 | 新合同且本次立场未明确时必问。 |
| 2. 合同阶段 | **合同目前处于哪个阶段？** 签署前／已签署、尚未履行／履行中或已有争议。 | 阶段未明确、且会影响修改对象或履行风险判断时问；对完整审查通常适用。合同日期或空白签章不能单独证明签署状态。 |
| 3. 处理方式 | **审核后如何处理？** 只给审查意见，不改合同／只在合同中加批注，不改正文／审查后按本技能底线及已确认条件直接修订合同。 | “审核一下”等未明确执行方式时问；已经要求修订 Word 或只审不改时直接沿用。 |
| 4. Word 交付版本 | **修改后的 Word 要哪种版本？** 清洁版（修改后的正文，无批注和修订痕迹）／修订批注版／两份都要。 | 已选择或明确要求修改合同，但交付版本未明确时问。仅审查或仅批注时跳过；用户“最终结论”不自动等于修改合同。 |
| 5. 交易边界 | **本单有哪些已谈妥、不可改动的条件或特别要求？** 无特别要求，按技能底线审查／有，请列明／尚未确定，相关事项先标待确认。 | 用户尚未说明时合并询问一次。例子可简列预付款、保函、责任上限、交期和不可改条款；不要求把合同所有参数重填。 |
| 6. 留痕署名 | **新增修订和批注使用什么署名？** 默认 SR，可指定其他署名。 | 产生修订或批注且尚未指定时作为可选附问；未答沿用 SR，不阻塞工作。只交清洁版时工作底稿默认 SR，无需另问。 |

第3项与第4项分开记录：前者决定是否能改正文，后者决定文件呈现。用户明确要求“按底线修改，只交最终无痕 Word”已同时回答两项；不能再要求一次“是否允许修改”的确认。若用户只说“最终状态”，结合上下文判断是报告最终结论还是合同清洁版；两者确实无法区分时只澄清对象。

信息获取后，用一两句话回显执行口径，例如：“本次代表乙方，按签署前合同审查；按已确认条件直接修改，交付清洁版和 示例署名 修订批注版。预付款比例保持不变，交期尚待确认。”随后直接执行，**回显不是第二轮批准**。

## 问题未回答时的处理

- 立场缺失：继续材料清点、文字提取和客观核算，等待立场，不代选。
- 正文修改权限未明确：只做审查；不得将工具预选项、沉默或等待超时当作修改授权。
- 已有明确修改授权但交付样式尚未回复：可以继续建立和验证留痕底稿，不因此停工；交付选择仍待用户答复。没有答复时可交付保留可追溯信息的修订稿并说明采用该呈现，不擅自清除历史留痕或声称用户选择了它。
- 阶段未明：完成不依赖签署状态的分析；不能默认为未签署并直接改写现行已签文本。已签合同的拟变更须标清是拟变更稿，必要时提供补充协议条款建议，不声称编辑 Word 已改变生效合同。
- 交易边界未答：沿用用户已明确的指令和当前材料，不把“合同里写了”自动当作“双方已谈妥不可改”。按技能审查，关键冲突、互斥选择或缺数值保持待确认；不补造事实。
- 署名未答：用 SR，保留历史作者。

## 只在材料触发时追加的问题

不把下列事项全部放入开场问卷：

- **基线版本**：多份合同并存且用户没有指定主版本时，列出实际文件名和差异线索，问以哪份为准；不得把两份内容自行拼成新基线。
- **历史修订**：要求清洁版而原件含未裁定的旧修订时，问“清洁版按接受现有全部修订后的文本、拒绝现有全部修订后的文本，还是逐项决定后的文本为基线？”用户已明确接受/拒绝或提供确认版时不再问。保留原件及完整留痕底稿，只在派生清洁副本中落实已确定处理。
- **争议与实际履行**：已签或履行中时，仅追问与发现有关的已付款、已交付、已开函、争议事件及目标；不要重新索取能从材料确认的数据。
- **参数冲突**：正文、附件或本次指令出现不同金额、比例、日期且无法依明确优先级解决时，列出冲突位置及后果，只问需决策的变量。其余独立修改继续。
- **批注读者**：用户特别说明内部意见、谈判底价等敏感内容，或要求直接供对方审阅时，区分内部说明与可对外批注；只在用途不明且会实质改变批注内容时问。生成文件不包含向对方发送的授权。

## 按选择交付

| 已确认选择 | 正文处理与交付 |
|---|---|
| 只给审查意见 | 原合同不变；给结论、证据、替换建议及待核实事项。只有明确要求 Word 报告时另做报告 DOCX，不自行生成修订合同。 |
| 只加批注 | 在副本加真实 Word 批注，原正文和已有修订不变；交付批注版。 |
| 修订批注版 | 在合同副本生成真实插入/删除修订及逐问题批注，按指定署名交付。用户明确只要修订、不加批注时服从该限定。 |
| 清洁版 | 在工作目录完成留痕修改及验证，再按已确认基线接受修订、移除批注，另存无痕 DOCX；仅交用户要求的清洁版。保留原件和内部留痕底稿。 |
| 两份都要 | 从同一个经验证的修订批注底稿派生清洁版；接受修订后两份正文一致，不能分别编辑后产生漂移。分别命名 `_清洁版.docx` 和 `_修订批注版.docx`。 |

“清洁/最终状态”只描述文档呈现，**不代表已签署、法律或业务无风险、未决事项已解决**。有待填参数、必要核实或未选择方案时，保持明确空项/待填标记，并在交付说明集中列出；不得为制作清洁版擅自选值。不能只因删除批注而把未决事项一起隐去。

清洁版与双版本的历史处理、一致性和渲染校验见 [修订与验证](revision-workflow.md)。确认过的信息仅在用户改变要求、切换新合同或主体/版本映射改变时更新；不每次续聊重问全套。
