# 版本与开发通道

本文件规定合同技能的发布纪律。技能可以继续扩展，但稳定版和开发版不得混用。

## 一、当前通道

| 通道 | 位置 | 用途 | 谁使用 |
|---|---|---|---|
| 稳定版 | 公开发布仓库的 `main` 与 `v1.2.0` 标签 | 已验证、可回滚的正式版本 | 同事、日常正式工作 |
| 开发版 | 本地开发工作区的 `.agents/skills/` | 真实合同试用、新功能验证、尚未定稿的修改 | 维护者、指定试用者 |
| Windows 安装 | 公开发布仓库 `develop` 的 `scripts/install.ps1` / `install.cmd` | 在 Win11 测试目录安装开发版 | 维护者、指定试用者 |
| 公共集成分支 | 公开发布仓库的 `develop` | 已脱敏、可供协作审查的下一版内容 | 维护者、外部协作者 |

稳定版以**标签**为准确认，不以 `main` 的最新提交为准。同事安装时必须固定到标签或 Release，不能跟踪 `main` 的最新变化。

## 二、开发流程

1. 在本地开发工作区的 `.agents/skills/` 开发和试用；真实合同、客户材料和审核成果只留在本地任务目录，不进入公开仓库。
2. 变更通过本仓库回归：语法/链接/frontmatter、Word 深读、红线、Office、审核工具、甲乙方条款库和未留痕改动检查。
3. 只把**通用、已脱敏**的改动复制到公开发布仓库的 `develop` 分支；真实参数、客户名称、账户、金额和合同原文不得复制。
4. 从 `develop` 拉短期功能分支，提交 PR 到 `develop`；CI 和人工审查通过后合并。
5. 需要试用时，从 `develop` 创建预发布标签（例如 `v1.3.0-rc.1`），试用者固定安装该标签。
6. 试用确认后，准备发布分支，更新 `VERSION`、`CHANGELOG.md` 和安装说明，合并到 `main`。
7. 在 `main` 打正式标签（例如 `v1.3.0`），创建 GitHub Release；保留旧标签用于回滚。

## 三、版本号

- `PATCH`：拼写、说明、无行为变化的修复；
- `MINOR`：向后兼容的新能力；
- `MAJOR`：技能名称、路由、输出格式或使用方式发生不兼容变化；
- `-rc.N` / `-beta.N`：试用版本，不得作为同事的正式安装源。

提示词、路由和技能描述的修改属于行为变化，不能只当作文档修改。

## 四、发布门禁

正式版至少完成：

1. 单元测试和脚本回归；
2. frontmatter、相对链接、缓存、软链接和工作区清洁检查；
3. 公开包敏感信息扫描；
4. 空项目安装测试；
5. Pi、Codex、DSH、Claude Code 的加载探针；Claude Code 同时核对 CLI 项目发现、桌面 Code 本地配置兼容及原生子代理注册，区分实际界面验证与配置/协议验证；
6. 本次新增能力对应的场景测试；
7. `VERSION`、`CHANGELOG`、Release notes 和实际内容一致。

涉及受理和类别界面时，必须包含目标宿主真实显示、明确提交回传与目标模型实际调用；原生加载、模拟UI回包、浏览器HTTP校验和桌面实机验收分别记录。只跑静态校验或协议初始化不能判定弹窗与多选功能通过。

不得因为“文件已生成”或“报告更长”判定通过。发现失败时修复根因，不用增加说明掩盖。

## 五、回滚

- 保留每个正式标签和 Release 产物；
- 安装脚本应支持固定版本，或先检出标签再安装；
- 回滚只切换安装版本，不删除开发分支；
- 不强制覆盖已被同事使用的标签。

## 六、不采用的默认做法

- 不把 `main` 的最新提交当作稳定版；
- 不在稳定分支直接做开发；
- 不用 fork 代替日常分支和 PR；
- 不把真实合同或未脱敏参数提交到公开仓库的任何分支；
- 不在没有回归和试用记录时提升正式版本号。
