# 保护性条款设计手册

在审核诊断已经用户确认、需要形成条款草案或补强方案时阅读。
本手册提供设计组件，不提供可以脱离角色、交易和现行法直接粘贴的“万能条款”。

1. 条款设计总框架
2. 标的、文件体系与变更
3. 交付、验收与质量保证

## 一、条款设计总框架

### 1. 从风险而不是模板出发

每条保护性条款都要回答：

- 对应哪个 finding ID 和已确认的商业目标？
- 我方是付款方还是收款方、交付方还是接收方、数据提供方还是处理方、权利许可方还是被许可方？
- 什么事件触发权利或义务？由谁判断，依据什么客观材料？
- 谁应在何时向谁发出何种通知？需要哪些附件或证明？
- 对方不履行程序时有什么后果？该后果是否与违约程度相称？
- 救济是继续履行、修复、重作、替换、减价、退款、赔偿、抵扣、中止还是解除？能否并用，如何避免重复获赔？
- 与验收、付款、质保、责任上限、解除、争议解决等条款是否冲突？
- 哪些数值、主体、权限和事实必须由用户确认？

使用“触发事件 → 通知/程序 → 客观标准与证据 → 期限 → 补救 → 后果 → 例外 → 存续/联动”的链条检查完整性。只写“双方协商解决”“乙方应赔偿一切损失”“甲方有权认定”通常不足以形成可操作机制。

### 2. 保护不等于无限偏向我方

- 保护的核心是履约时“拿得到”：可收款、可交付、可举证、可免责、可退出，而不是堆高罚则或写一串无法启动的权利。
- 法律底线、合同可执行性、商业首选方案和可退让方案分别记录。
- 不用格式条款不合理地免除我方责任、加重对方责任或排除对方主要权利；不要假设签字盖章就能解决效力和提示说明问题。
- 我方提供格式文本时，对我方有利的异常重锤条款也要清单化，安排合理提示、按要求说明及证据留存；不能只审查对方模板。
- 责任上限、间接损失排除、验收视为通过、单方解释权、自动续期、管辖及送达条款都要做对方视角的反执行测试。
- 不用“一切”“任何”“绝对”“永久”“无条件”代替边界。确需宽泛措辞时，先列出必须保留的法定例外和商业例外。
- 不虚构价格、税率、日期、违约金比例、责任上限、授权人员或附件。缺变量时使用 `[待确认：……]` 并进入待确认清单。

### 3. 已确认方案的闭合授权与最小改写

用户确认一组方案，是授权把这些方案写成可执行条款，不是授权继续扩张或收窄交易。
先逐项抄写确认原句，再做最小必要改写。不能为了显得完整、专业或更保护我方，自行添加
新的损失类别、责任例外、认知条件、裁判/确认前提、保险抵扣、动态上限、转让/使用限制、
免费服务或其他实质义务。

区分两类补全：

- **程序补全**：在已确认机制内补充不改变利益分配的表格、通知方式、材料清单或必要占位；
  仍需记录，未确认数值不能直接填具体值。
- **实质变更**：新增/合并/收窄权利义务，或附加“仅”“知道或应当知道”“经生效裁判”
  “双方确认”“附带/后果性”“随变更调整”等会改变责任范围的语义。未获确认时，只能列入
  单独的未纳入草案建议/Q-ID，不得写进可落笔正文。

写完做反向语义 diff：从每款正文回查确认原句，逐句记录对应、扩张、收窄和新增；再检查
跨条款组合是否产生原方案没有的结果。触发事件按主体、行为、完整性、资料、送达/收到和
起算点逐项核对；“完整提交”不能弱化为“提交申请”。把必须保留的短语建成锚点，字面核验后
仍须检查上下文。一致性表中的“照录”“无偏差”必须由逐字引文支持，
不能让同一草稿的作者只用自检结论自证。

### 4. 条款卡片

每个条款提案按以下结构形成：

```text
C-编号｜对应 R-编号｜条款名称
确认方案原句与闭合授权边界：
保护目标与适用立场：
建议文本：
逐句反查与语义差异：
待确认变量：
联动条款：
法律核验状态：
首选方案 / 可退让方案（如用户需要谈判版本）：
```

## 二、标的、文件体系与变更

### 1. 标的和范围

保护接收方时，明确名称、型号、数量、质量、功能、技术资料、附随服务、交付物形式及不包含事项；保护提供方时，同样要封闭范围边界，避免“满足甲方一切需求”“所有相关服务均包含”。

至少检查：

- 技术参数、样品、图纸、需求清单是否可识别且有版本；
- 主合同中的“工作成果”“设备”“服务”“交付日”“验收”是否定义一致；
- 谁提供材料、环境、接口、场地、许可证、数据和人员；
- 第三方产品、开源软件、分包服务和客户自备项是否划清责任；
- 附随义务是否有完成标志，而不是只有抽象“协助”。

### 2. 文件优先级

优先级条款要与实际签约权限和变更程序联动：

- 列明主合同、补充协议、订单、技术附件、报价、投标文件、订单确认、数据处理附件的组成与版本；
- 区分“同层级后签文件优先”和“专项文件仅就专项事项优先”；
- 订单要变更主合同责任上限、知识产权、争议解决等重大条款时，可要求明确点名被变更条款并由有权代表签署；
- 不接受由一方单方解释、单方更新网页条款或未提供文件自动约束我方的安排，除非我方能控制该机制且已通过效力审查；
- 背靠背引用上游文件时，先确认对方是否取得并能提供该文件、我方是否有能力履行、相关义务是否与本合同主体和价款相匹配，不能仅写“全部上游义务自动传导”。

### 3. 变更机制

完整变更单至少包含：变更内容、原因、对费用和税费的影响、对工期/里程碑的影响、资源与依赖、验收标准、生效时间、授权签署人。

保护提供方：未经授权变更不扩大工作范围，继续原范围不构成违约；紧急指令也要事后补签和留证。
保护接收方：变更不得由沉默或一般项目沟通自动推定；未经批准的额外费用不予承担，但应避免忽略实际受益、追认或法定责任。

## 三、交付、验收与质量保证

### 1. 交付

把发货、运输、到货、卸货、安装、调试、上线、资料移交、初步验收和最终验收拆成可证明的事件。分别约定：

- 时间、地点、负责人和所需条件；
- 运输、保险、包装、保管及费用承担；
- 所有权转移与毁损灭失风险转移是否分离；所有权保留、登记、实际交付和第三方仓储凭证是否足以支撑执行/破产场景，存在裁判分歧时标存疑而非断言；
- 签收仅证明收到，还是同时证明数量、外观或质量；
- 第三人收货、分期交付和部分交付的效果；
- 单证、源代码、账号、密钥、手册等是否属于交付物。

### 2. 验收

客观验收条款至少包含：完整提交标准、验收依据、测试环境、样本和测试用例、验收期限、缺陷分级、书面通知内容、修复与复验、部分验收、视为验收（如有）、隐蔽瑕疵和质保衔接。

**我方为接收方**时重点防止：

- 过短期限覆盖全面性能或隐蔽瑕疵；
- 签收、付款、试用、沉默被推定为放弃全部质量权利；
- 验收后才发现的缺陷没有救济；
- 反复修复却没有替换、退货、减价或解除出口。

**我方为提供方**时重点防止：

- 验收以对方或其客户“满意”为唯一标准；
- 对方不验收、不反馈导致付款和上线无限期悬置；
- 轻微缺陷阻止全部验收和全部付款；
- 视为验收被写成排除隐蔽缺陷、故意隐瞒或法定权利的不合理免责。

视为验收机制如被采用，应以完整提交和客观可验事项为前提，设置合理期限、提醒和异议程序，并明确不覆盖哪些依法或依约不得排除的权利。证据链至少核对：催告及送达、验收排程登记、可复核测试记录、对方反证和推翻机制；不能由一方仅凭自己的日志“自导验收”。

### 3. 质保与售后

明确质保起算点、期限、范围、排除事项、响应与恢复时间、备件、费用、修复后质保、重复故障升级救济、停机和替代方案。区分维修、重作、更换、退货、减价、赔偿及解除的适用条件，避免“维修是唯一救济”不合理封死出口。

## 四、价格、税费、发票与付款

### 1. 价税拆分

- 分别列不含税价、适用税率/征收率、税额、含税总价，复算分项与总额、大小写和其他文件。
- 税率、税目和拆分必须符合真实交易及审核日税法，不为套模板或降低税负虚构货物、服务、无形资产等拆分。
- 写明税收政策变化时不含税价或含税价如何调整、由谁承担，不能同时固定净价和总价又约定税率变化自动调价。
- 发票类型、项目、金额、开具时间、交付方式、错误发票更换和实际损失承担应与付款机制协调；开票、纳税义务和付款现金流的先后分别分析，不混成同一时点。

### 2. 付款条件和期限

列明每期金额/比例、触发事件、完整付款资料、期限起算点、账户核验、付款日和节假日处理。比例之和、各期金额和总价必须勾稽。

- 保护付款方：可约定交付、验收、资料或发票等条件，但应评估主给付义务与附随义务的关系，避免把轻微发票瑕疵写成无限期拒付全部价款的当然依据。
- 保护收款方：避免付款完全受对方内部审批、第三方付款或最终客户满意控制；如接受背靠背付款，明确第三方事件、催告、最长截止日、举证和例外。对验收僵局另设可证明的到期出口，不让“未验收”同时消灭付款到期、逾期责任和解除权。
- 逾期暂停/中止和解除要与已完工作结算、无争议金额支付、通知、恢复条件及责任边界联动；暂停期间是否顺延、是否计责必须明确。
- 保留款、质保金、抵扣和暂停付款须有基数、比例、期限、通知、争议金额与无争议金额分离及释放条件。
- 第三方代付、债权转让、账户变更要规定核验与通知，不把“禁止转让金钱债权”写成当然可对抗一切第三人的效果。

## 五、知识产权、保密与数据

### 1. 知识产权

先分类再分配：背景成果、定制成果、通用工具及其改进、第三方材料、开源组件、数据、文档、商标和宣传素材。

条款至少处理：权属或许可、许可标的、地域、期限、主体范围、是否可转让/分许可、使用目的、复制备份、修改、源文件/源代码交付、费用、第三方权利清理、侵权通知与抗辩、替换/修改/退款等救济。

- 接收方不能只写“成果归我方”，却遗漏背景技术使用权和交付形式。
- 提供方不能笼统让渡全部既有方法、工具和后续改进；也不能以保留背景权利使定制成果实际无法使用。
- 付款与权利转移挂钩时，明确对应费用和已付款成果范围，避免全部权利因小额争议被不当冻结；与便利解除、部分履行结算和成果移交同步检查，不能出现已支付对应费用却仍无法使用已移交成果的权利真空。
- 销售含有软件或技术的设备，不当然等于相关知识产权全部转移。

### 2. 保密

明确保密信息、载体、例外、允许接收人、使用目的、保护措施、依法披露程序、返还/删除、泄露通知、期限及违约责任。一般保密信息的固定期限与商业秘密保护分别处理，不用统一短期限意外削弱商业秘密，也不盲目要求所有信息永久保密。

### 3. 数据与个人信息

按实际角色处理：数据类别和来源、处理目的和期限、委托或共同处理关系、最小必要、访问控制、分包、跨境、事件通知、协助响应、审计证据、返还删除及删除证明。

安全事件通知应包含知悉时点、初始通知与持续更新、事件范围、影响、处置和联系人；不要只写小时数而没有其他机制。涉及个人信息、重要数据或跨境时进行专项法律核验。

## 六、违约、赔偿、责任限制与担保

### 1. 违约责任

逐项对应核心义务设置可执行的违约后果，写清计算基数、起止日、上限（如有）、催告/修复期、继续履行、损失差额和解除的关系。违约金可能依法调整，不在报告中保证固定比例必然得到支持。

定金、订金、预付款、押金和保证金不得混用；定金与违约金并存时分析法定适用关系，不设计双重处罚。

### 2. 赔偿与第三方索赔

区分直接损失、可得利益、间接损失、第三方索赔、行政责任和实现债权费用。律师费、保全费、担保费、公证费、鉴定费、差旅费等应明确是否纳入及合理性/实际发生/凭证要求。

第三方索赔机制包括及时通知、信息提供、抗辩参与或控制、和解同意、减损、赔付凭证和重复赔偿禁止。迟延通知是否导致全部丧失赔偿，应与实际影响及公平性一起审查。

### 3. 责任上限与排除

- 写清上限基数（合同总价、相应订单、已收/已付费用等）、期间和是否含违约金、退款、价款返还及费用。基数随收付款或实际发生额变化时，代入签约/未付款、部分付款、全部付款等场景，检查上限为零、责任倒挂或例外失效；分项帽与总帽并存时明确适用顺序和不重复封顶；应退货款本金是否另计须写清，不能用含糊措辞制造第三层责任。
- 分别审查人身损害、故意或重大过失、知识产权、保密、数据、欺诈等例外，不机械地全部无限或全部封顶。
- 间接损失排除与第三方索赔、约定违约金、数据恢复费、替代采购差价之间要协调。
- 同一风险不能既完全排除又另行承诺全额赔偿，除非明确优先关系。

### 4. 增信与保险

保证、抵押、质押、保函、保险、所有权保留等分别核查主体权限、形式、范围、期间、登记/交付、主合同变更影响及实现程序。公司担保、保证期间和登记事项须专项核验，不能只加一句“关联方承担连带责任”就视为风险已经消除。

涉及保函或分次释放担保时，另核：申请人是否就是义务人、开立人/受益人主语是否一致、主合同和索赔声明是否对应；有效期是否覆盖履行及索赔窗口，延期义务是否有可执行预判期；目标余额、本次释放额和分次索赔后余额能否复算；释放后剩余额度是否仍覆盖质保等后续风险。固有残余风险不能写成已通过一句兜底消灭。

## 七、中止、解除、退出与存续

### 1. 中止与解除

为重大违约、长期迟延、反复质量失败、资信恶化、违法、数据事件等设计适当的中止或解除机制：

- 触发事实和证据；
- 是否需要催告、补救期，哪些情形可立即处理；
- 全部或部分解除、分批订单是否隔离；
- 通知到达和生效时间；
- 已履行部分结算、退款期限、替代履行和损失赔偿；
- 担保、违约责任和争议条款是否继续。

避免“任何违约均可立即解除并不退任何款项”这类明显失衡安排。法定解除与约定解除分别分析，合同解除不当然抹除结算、清理和既有违约责任。

### 2. 便利解除与退出

如允许便利解除，明确通知期、已完成且符合约定工作的计价、已承诺且不可取消的合理成本、材料/成果归属、未履行部分费用和预期利润是否排除。不要只写“可随时解除”，却没有交接和结算。

退出清单可包括：数据导出格式、迁移协助、账号与密钥、源文件、在制品、备件、返还/删除、业务连续性、人员与分包方配合、最终账单及证明。需要存续的保密、知识产权、责任、审计、结算和争议条款逐项列明。

结算按顺序走通：确认已履行及合格工作量 → 计算未履行部分减价/退款 → 明确已付款抵充顺序 → 确定返还期限与担保调整。争议金额与无争议金额分离，不能把“争议解决完毕”设为一切返还的前置；上游不能退款是否阻塞无争议返还也要单独评价。

## 八、不可抗力、情势变更与业务连续性

分别处理不可抗力、一般商业风险、供应链波动、价格变化和情势变更，不把任何成本上涨都自动归为免责事件。

不可抗力条款核查通知、证明、减损、影响范围、部分免责、迟延后发生事件、持续一定期间后的解除和已到期金钱义务。情势变更不以单方通知当然改价或解除；需要自动调价时，另设客观指数、公式、阈值、周期、证据和上限，并做法律核验。

对关键服务可补充备份、灾备、替代人员、数据恢复目标、关键分包方替换和应急沟通，但这些商业连续性义务与法定不可抗力规则分开。

## 九、通知、证据、争议解决及其他机制

### 1. 授权与通知

区分项目联系人、变更授权人、验收签署人和合同解除/索赔通知接收人。联系方式变更、送达方式、到达时点、退件和电子证据保存应可操作。实际签收、无正当理由拒收、地址未通知变更、发送方写错地址和系统退件分别设置结果，不用单一“发出即送达”覆盖所有情形。诉讼/仲裁文书送达约定单独做效力审查，合同通知机制不替代法院依法送达，也不承诺所有“视为送达”表述都会被支持。

### 2. 证据与记录

围绕付款、验收、变更、授权、质量异议、通知、数据删除和解除设置记录义务。明确系统日志、邮件、电子签名、订单、对账单、检测报告和会议纪要的证据用途；会议纪要能否变更合同仍应与授权和变更条款一致。

### 3. 争议解决

检查法院管辖连接点、仲裁机构可识别性、法院诉讼与仲裁是否混用、主从合同和关联合同是否一致、准据法、语言、保全与临时措施、送达和境外执行。不要同时保留互相排斥的终局机制，也不要为提高我方便利而虚构连接点。

### 4. 其他常见机制

按交易需要检查：转让与债务加入、分包和更换分包方、抵销、审计、保险、反商业贿赂、出口管制、宣传使用名称、独立主体关系、可分割性、完整协议、弃权、文本语言、电子签署、份数和生效条件。

可分割性不能挽救依法导致整体无效或合同目的不能实现的核心条款；“未行使权利不视为弃权”也不能替代法定期间管理。

抵销、暂扣和扣款要审查绝对排除法定权利的可执行性，并明确争议/无争议金额、通知、举证和结算程序；不得用“任何情况下均不得抵销”掩盖机制风险。签署页特别确认表只摘录正文真实存在的口径、条件与后果，不用摘要反向创造新义务。

## 十、谈判梯度与交付前联动检查

### 1. 需要谈判方案时

为每个重要条款分别给出：

- **法律底线**：不可通过商业让步排除的强制要求；
- **首选文本**：最符合我方利益且仍可执行；
- **可退让文本**：保留核心救济，让渡程序、金额或期限；
- **最低保护**：退让后仍必须具备的通知、证据、责任或退出机制；
- **风险接受项**：由用户在知情后决定，不把商业接受写成法律风险消失。

没有用户要求时，不堆砌多个版本；先给一套主建议并列关键可谈变量。

### 2. 条款草案完成后的联动检查

1. 每个 C-ID 都能回溯到已确认 R-ID；没有夹带未授权修改。
2. 新定义、主体、日期、金额、税率和附件名与全文一致。
3. 验收—付款—质保—违约—解除之间没有形成逻辑死循环或权利真空。
4. 责任上限、例外、违约金、赔偿、退款和第三方索赔不冲突、不重复获赔。
5. 主合同、订单、附件和关联合同的优先级与修改权限一致。
6. 法律底线未因谈判版本被突破；所有法律命题已核验或明确标注待核验。
7. 所有待填变量集中列出；没有把示例数字当成交易数字。
8. 如后续写入 docx，另行遵守修订/完善模式的确认、备份、dry-run、verify、重新 extract 和变更日志要求。
