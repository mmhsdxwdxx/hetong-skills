# 深度审核方法与覆盖清单

在执行全文扫描、跨文件勾稽、反方复核和交付前质量门禁时阅读。
本文件与 `hetong-craft` 的审查总清单、风险模式库叠加使用；项目规则和已锁定交易红线优先。

## 目录

1. 多轮扫描法
2. 机械一致性与数字复算
3. 全生命周期风险清单

## 一、多轮扫描法

不要一边读第一段一边零散写结论，也不要只做一次关键词搜索。按以下轮次推进，每轮保留记录：

### 第 1 轮：冷读与交易还原

先完整阅读全部提供文本，再写审核结论。还原：主体及角色、交易目的、标的、对价、履行顺序、关键里程碑、第三方、合同族、文件优先级、退出路径。

冷读阶段发现的问题先记候选，不急于定性；后续条款可能定义、限制或推翻初步理解。

### 第 2 轮：机械完整性扫描

检查名称、主体标识、定义、编号、交叉引用、附件、空白、签署、日期、金额、税率、比例、期限、账户变更、文本语言和格式异常。该轮不依赖商业立场，也不能代替法律与商业审查。

### 第 3 轮：逐条权利义务扫描

对每一条问：

- 谁做什么、为谁做、何时做、在哪里做、以什么标准做？
- 谁判断完成，需要什么证据，费用由谁承担？
- 不履行或第三方原因导致不履行时，谁有何救济？
- 本条与前文定义、后文责任及附件是否一致？
- 对我方是保护、义务、限制还是授权？条件是否对等、可执行？

### 第 4 轮：缺失机制扫描

“全文没有”本身只有在通读正文、附件和关联文件后才能成立。按交易生命周期、单方权利和合同类型找缺口，不以模板条款数量判断完备性。普通货物买卖未必需要数据条款，简单保密协议也不应硬塞建设工程条款。

### 第 5 轮：法律与可执行性扫描

按 `legal-verification.md` 核验特别法、强制规则、任意性补缺、格式条款、免责、生效、授权、期间和争议解决。分别评价效力、可执行性、举证和商业风险。

### 第 6 轮：跨文件与失败场景扫描

执行第三至第五部分的勾稽与压力测试，重点找单条阅读无法发现的组合风险。

### 第 7 轮：反方与交付复核

站在对方、法官/仲裁员、履约人员和财务人员视角反驳每条 finding：是否有别解、是否已有其他条款兜底、是否真的可执行、是否值得谈判。最后执行覆盖矩阵和权限检查。

## 二、机械一致性与数字复算

### 1. 文本与结构

- 合同名称、编号、版本、主体全称/简称、统一社会信用代码、地址、签署人及印章名称是否一致；报告中对敏感号码可脱敏。
- “甲方/乙方”“买方/卖方”“委托方/受托方”等是否混用导致角色颠倒。
- 定义是否未定义、重复定义、定义后偏离、循环定义或包含实质义务。
- 条号、款项、附件名、交叉引用、引用条款是否实际存在且内容匹配。
- 空白、待定、删除线、批注、修订痕迹、隐藏文字、页眉页脚、文本框和扫描图片是否漏审。
- 生效、签署、交付、验收、付款和终止日期是否存在先后矛盾或不可能期间。
- “以上/以下/以内/届满/工作日/自然日/书面/及时/合理期限”是否有统一、可执行口径。

### 2. 数字必须独立重算

不得只核对两处数字是否相同。建立数字台账，至少覆盖：

| 类型 | 复算与勾稽 |
|---|---|
| 价税 | 不含税价 × 税率＝税额；不含税价＋税额＝含税价；含税价÷(1＋税率)＝不含税价；税率适用另行法律核验 |
| 分项与总价 | 单价×数量、各分项、优惠/折扣、币种、总价与大小写是否勾稽 |
| 付款 | 各期比例之和、金额之和、保留款、质保金、已付/未付、付款触发和起算日 |
| 违约与赔偿 | 日/月/年比例、基数、起止、上限、定金与主合同标的额、损失差额和重复计算 |
| 期限 | 工作日/自然日、起算事件、届满日、顺延、通知/催告/补救期、质保和保证期间 |
| 订单与关联合同 | 数量、金额、税率、日期、上限基数、折扣和结算条件是否一致 |

复算时保留公式、原值、结果、差异和受联动条款。四舍五入规则、币种、含税/不含税口径和单位（元/万元）必须明确。分项小计→分部→合计→含税总价应分层加总；分批/逐台/总量、责任分项帽/总帽、担保目标余额/释放额/索赔后余额也要能互相勾稽。涉价税合同必须分别列出合计不含税、合计税额、合计含税三项，不能只算分项或总价差。

`review_kit.py numbers` 用于高召回候选，`calc-tax` / `sum` 或其他 Decimal 工具用于实际计算；不能只跑 `search --numbers` 或引用构建脚本的断言充当独立复算。模板审核另建“样本值→占位符”映射，检查示例数字残留和公式自洽。

期限链要逐步推演起算、催告、补救、解除、退款、交单和担保调整。工作日/自然日、是否包含起算日、法定节假日与调休分别判断；跨节假日至少抽取代表性日期复算并记录日历依据，不凭周末直觉。

税率本身是否合法适用与算术正确是两个问题：算对不代表税目、税率或交易拆分正确。示例、模板或历史合同数字不能直接成为本合同数字。金额大小只说明敞口规模，不等于已证实损失。

## 三、全生命周期风险清单

按交易适用性裁剪，不机械要求每项都有独立条款。

### 1. 缔约、主体与授权

- 主体是否真实、适格、有权签约；资质、许可、内部审批、代理、代表和担保授权是否需核验。
- 预约/本约、成立/生效、批准/登记、签署形式、电子合同和实际履行是否区分。
- 陈述保证、披露、先决条件、投标文件/报价/宣传是否进入合同。
- 格式条款、重大利害条款提示说明、消费者/劳动者等特别保护是否涉及。

### 2. 标的、范围与质量

- 标的、数量、功能、技术标准、样品、图纸、成果形式和排除范围是否确定。
- 法规/标准更新、第三方标准、客户特殊目的和通常质量标准如何协调。
- 材料、场地、环境、接口、数据、人员、许可证及其他配合义务由谁承担。
- 附随资料、培训、备件、维护、迁移、源文件和售后是否遗漏。

### 3. 交付、验收、所有权与风险

- 发货、到货、安装、调试、上线、交付资料和各阶段验收是否区分。
- 验收标准、程序、期限、缺陷分级、复验、视为验收、隐蔽瑕疵、部分验收是否可操作。
- 所有权、风险、保管、保险、签收和付款是否被错误捆绑。
- 分批、部分、第三人交付和拒收后的处理是否明确。

### 4. 价款、税务、发票与付款

- 价税、币种、计价单位、费用边界、调价、折扣、对账、税率变化是否完整。
- 付款条件、起算点、资料、发票、账户、第三方收付、抵扣和保留款是否协调。
- 内部审批、最终用户验收、上游回款等第三方条件是否使付款无限悬置。
- 拆分交易与“三流”材料是否符合真实交易和税务证据要求；不把经验性口径误称为所有合同的绝对法定要件。

### 5. 变更、转让、分包与第三方

- 变更授权、书面形式、费用/工期影响、紧急变更和未批准工作的后果。
- 债权转让、债务转移、合同概括转让、债务加入和通知/同意是否区分。
- 分包范围、资质、同意、替换、责任传导和分包方直接权利是否明确。
- 关联方、最终客户、承运人、平台、供应商和实际履行人的责任边界。

### 6. 知识产权、保密、数据与合规

- 背景/前景/第三方/开源成果、权属/许可、使用范围、交付与侵权救济。
- 保密信息、例外、目的限制、接收人、返还删除、期限和商业秘密。
- 数据角色、处理目的、安全、分包、跨境、事件、审计、删除和协助。
- 反商业贿赂、产品安全、环保、出口、制裁、反垄断、劳动用工等专项风险按交易触发。

### 7. 违约、责任与增信

- 核心义务是否有对应违约后果；催告、修复、继续履行、替代履行和减损是否衔接。
- 违约金、损失、定金、退款、赔偿和实现债权费用是否协调。
- 责任上限基数、期间、例外、间接损失、第三方索赔和重复获赔是否明确；基数为“已收/已付/实际发生/相应订单”等动态金额时，代入签约或未付款、部分付款、全部付款等时点复算，检查上限为零或保护倒挂。
- 保证、抵押、质押、保函、保险、所有权保留的主体、形式、范围、期间和实现程序。
- 人身损害、故意或重大过失等法定免责限制是否被违反。

### 8. 中止、解除、终止与退出

- 约定/法定解除、催告/补救、立即解除、部分/分批解除、解除通知和异议。
- 中止履行、恢复条件、担保和持续不能履行后的出口。
- 结算、退款、移交、数据导出、在制品、迁移、替代服务和最终对账。
- 结算清理、保密、知识产权、责任、审计和争议条款的存续。

### 9. 不可抗力、情势变更与连续性

- 事件定义、通知、证明、减损、影响范围、部分免责、迟延后事件和长期持续。
- 商业风险、价格变化、供应链问题与不可抗力/情势变更是否混淆。
- 备份、灾备、替代履行、恢复目标和应急沟通是否符合业务需要。

### 10. 通知、证据与争议

- 通知联系人、变更授权、验收权限、地址、方式、到达与变更通知。
- 对账、验收、变更、质量异议、会议纪要和系统记录的证明作用。
- 诉讼/仲裁是否冲突，机构/法院是否明确，连接点、准据法、语言、保全、送达和执行。
- 主从合同、关联合同的争议条款是否会造成同一交易多程序并行且无法协调。

### 11. 单方权利与商业锁定

按 `stance-and-negotiation.md` 检查单方调价、变更范围/标准、最终解释、对账扣款、暂停、审计、解除、自动续期、网页政策更新和单方转让等安排：是否有客观条件、通知、证据、异议、补偿和退出，而不是见到“单方”就机械判错。

另查最低采购/消费、排他、最惠待遇、不招揽、数据不可导出、源代码缺失、迁移协助、不可替代供应商、交叉违约/解除等锁定效应。写清锁定期限、退出成本和替代路径；法律有效不等于商业上可接受。

### 12. 文风、体例与签署文本

语言问题与实质问题分别登记，避免句式偏好挤占重大风险。文风建议不得改变数字、期限、义务分配、条件结构或引用关系；删掉某表述会损失法律精确性时，不为“简洁”而删除。

核对正文、附件、签署页摘要、特别确认表和回执是否一致；过程批注、审核标记与合法签署空位、经确认保留的待填项分别处理。

## 四、跨条款、跨合同与主体检查

### 1. 必做勾稽链

- 定义 → 标的 → 交付 → 验收 → 付款 → 质保 → 违约 → 解除 → 责任上限。
- 主合同 → 补充协议 → 订单 → 技术附件 → 报价/投标 → 数据/保密附件。
- 正文 ↔ 附件/回执/签署页摘要；修订说明/任务书 ↔ 正文实际落点。
- 我方义务 → 上游权利 → 下游义务 → 第三方配合 → 违约责任与保险/担保。
- 含税价格 → 分项税率 → 发票项目 → 付款金额 → 会计/对账材料。

### 2. 多主体与背靠背

绘制主体和合同关系图，避免把非签约方直接当作义务人，也避免关联方简称混用。背靠背审查至少问：

1. 上游文件是否提供、是否有效、版本是否固定，我方是否实际知悉并能履行？上游支撑仅为拟取得时，不得写成已经取得。
2. 哪些义务需要传导，是否与本合同范围、金额、期限、责任上限和争议机制相容？
3. 上游验收、付款、变更和解除对我方有何影响，是否有最长截止日和替代救济？
4. 下游承担的责任是否足以覆盖我方对上游的责任，缺口由谁承担？
5. 是否发生不同主体、不同税目或不同法律关系的错误“穿透”？

不要把“背靠背”当成当然有效、当然免责或所有上游条款自动并入的结论。

## 五、履约失败场景压力测试

选择与本交易相关的场景，用合同原文逐步推演“通知—证据—费用—责任—退出”：

- 对方迟延或拒绝付款、发票错误、账户被变更、第三方不付款；
- 交付迟延、数量短缺、隐蔽缺陷、反复修复、验收拖延或第三方不验收；
- 需求反复、对方不配合、关键依赖失败、分包方违约、人员流失；
- 知识产权索赔、数据泄露、保密信息被用于竞争、宣传侵权；
- 对方资信恶化、失联、破产、股权/控制权变化、资质被撤销；
- 不可抗力、价格剧烈变化、政策调整、系统中断和供应短缺；
- 我方需要暂停、部分解除、全部退出或更换供应商/客户；
- 发生争议时需要证明授权、变更、验收、通知、损失和送达。

每个场景记录：现有条款能否处理、证据在哪里、是否出现权利真空/逻辑死循环、对应哪个 R-ID。压力测试用于发现机制缺口，不把假设事件写成已发生事实。

## 六、findings 的证据化与风险校准

### 1. 一条合格 finding 的最小结构

```text
R-ID｜标题（跨轮稳定；合并/拆分保留映射）
关联 Q-ID：需要用户拍板的事项；无则写“无”
定位：文件 ID＋条款名称/编号＋提取定位
原文或缺口：精确引文；缺失须说明已核范围
结论状态：已证实 / 合理推断 / 待补事实 / 待法律核验
风险类别：事实错误 / 内部冲突 / 效力与合规 / 权利失衡 / 机制缺失 / 可执行性 / 证据 / 文字歧义
影响：对我方的具体触发场景和后果
依据：合同条款、复算、已核法律或明确标注的商业判断
反方复核：主要别解、例外、其他条款是否已兜底
第二路径与结果：S1/S2 必填；其余按需要
修订方向：只写诊断层面的处理机制，不给可粘贴成稿，不自行拟定商业数值
保护条款需求：需要建立的机制，完整文本待用户确认
```

### 2. 风险等级与处置分开

- **S1 阻断**：不解决原则上不应签署/用印，或核心交易目的、效力、履行与关键救济存在重大断点。写明构成路径，不因金额大或措辞严厉就定 S1。
- **S2 重大**：对价款、交付、验收、核心权利、重大责任、背靠背承接或退出有实质风险敞口，建议本轮优先解决。
- **S3 一般**：明确但非致命的歧义、程序、证据、操作或一致性问题，可择机修订或签后管理。
- **S4 建议**：体例、表达和优化事项；不挤占核心风险，也不硬凑成签约阻断。

发生可能性可另标高/中/低/无法判断，不与影响程度混成无依据的数学分数。处置另列为签前必改、优先争取、确认后接受、文字修正、签后履约关注。法律后果（无效、可撤销、不成为合同内容、约定不明补缺等）单独评价，不与 S1–S4 机械一一映射；用户接受商业风险不等于违法安排变为合法。

### 3. 定级反证、第二路径与修正记录

定级前逐条反证：不利解释是否已有协调路径；程序缺失是否已有法定救济；同一根因是否被拆分重复计数；金额是否被误写成已发生损失；是否为了显得严格而升级，或为了放行而降级。

S1/S2 至少用第二路径复核（原文复读、关联文件互证、独立复算或正式法源），并记录路径和结果。复核后合并、撤回或调整等级时保留“原判断→新判断→反证理由”，不得偷偷删改让报告显得始终正确。

### 4. 排除伪 findings

- 引文不存在、定位错误或漏读上下文；
- 把任意性默认规则当成强制要求；
- 把商业不利直接写成合同无效；
- 只凭“没有模板条款”而不分析交易是否需要；
- 忽略关联合同或附件已有安排；
- 假设未提供的事实已发生；
- 为凑数量重复同一根因，或把纯个人写作偏好当风险。

## 七、覆盖矩阵和反向质量检查

交付前做两次反向遍历：

1. **从文件到 findings**：每个文件、每章、每个附件和每个排除项都有阅读/检查记录；没有只审关键词命中的条款。
2. **从 findings 到文件**：每条结论都能回到原文、复算、法律来源或明确假设；每条保护需求都能回到 R-ID。

再检查：

- 报告是否回答“能不能签、签前改什么、为何改、怎么补、还有哪些不能接受”；
- 是否把我方角色、对方视角和可执行性同时考虑；
- 是否披露未提供附件、OCR/提取限制、事实缺口和未核法律；
- 是否区分诊断、条款草案和实际修订，没有未授权写入；
- 结构门禁、引用核验和复算脚本是否只被当作辅助证据，而未冒充法律、税务或商业合规结论；
- 是否给出集中、最少但足够的用户决策项，而不是用数十个非关键问题阻塞交付。
