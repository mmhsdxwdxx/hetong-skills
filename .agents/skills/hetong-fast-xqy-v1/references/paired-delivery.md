# 详细报告与原稿批注稿

## 固定职责

| 交付物 | 内容 | 不应做的事 |
|---|---|---|
| `合同名称_v版本_XQY审核报告.docx` | 八项大纲；R事项的依据、详细分析、本方固定条款、具体文字修订建议及待确认参数 | 只说“建议修改”却不给改法；把建议写成已执行 |
| `合同名称_v版本_XQY批注稿.docx` | 保留无须修改的原文、字体、版式及历史；同号原生批注，明确错误按清单作真实修订 | 将合同正文统一改宋体；自动接受历史；将详细建议重复塞满批注；擅自落实未确认商业方案 |

报告正文沿用11pt宋体。批注稿保留输入格式，不能为了与报告统一而改原稿。没有correction时是仅批注副本；有correction时是保留真实修订的副本，不能把一般建议说成已实施。

默认调用包含两份交付授权。一般建议只加批注；correction仅实施已判明的明确错误及中英同步，源文件和历史仍只读。普通红线修改仍按craft的确认与修订流程，不能借本分支绕过。传统受理回执如已存在，按其有效范围和本次最新授权核对；不伪造类别回执为生成器放行。

## R编号

- 首轮用`R-001、R-002……`给每个独立事项编号，跨八项统一递增，不在每一项重新从1开始。后续同一合同版本链沿用原ID，新问题续号；已删除或合并的ID留映射，不重排挪用。
- `revise`＝建议修订；`attention`＝履约注意；`verify`＝实质待核实；`correction`＝本轮已执行的明确纠错。它们是处理类型，不另造风险等级。
- 一事项对应详细意见中一个完整R小节，Word每处相关批注显示同号。一个物理段落含多个事项时可合为一条批注，逐项独立说明；不得向对方转介报告。
- M/A/B是固定条款来源，RL是本次基线段落定位，Word批注数字ID是内部标识；它们均不替代R号。内部映射记录四者关系，不让使用者猜对应关系。
- 批注示例：`R-001｜建议修订：开票条款缺少错误更正义务及逾期处理，建议明确责任和处理期限。`
- 注意示例：`R-002｜履约注意（正文保留）：支付前核验经办授权，并保存按批次确认的交接清单。`

同一目录两份文件使用同一版本号。文件名、报告位置、R编号在两份交付同号显示；文件名、Word数字ID和锚点的技术对应关系仅存映射，批注不出现文件指引。适用[审阅隐私铁律](../../hetong-word/references/review-privacy.md)，不因尚未外发而放宽。

## 事项质量和锚点

报告每个需修订事项必须给出可直接阅读的替换、新增或删除建议文字，并明确待确认变量及插入位置。注意事项应说明具体履约动作、触发点和证据；仅“符合Mxx、建议保留”不自动生成批注。

批注说明应独立可理解，通常一两句；必要的事实、理由及处理方向直接写清，不通过“详见”把理解负担转给另一份文件。复杂计算、完整建议条文、长法源及跨条款论证可另留内部报告。注意类可用于已具备条款但有实际操作提醒之处，这是用户指定的快审交付形式，不推广为普通审核的批注配额。

锚点使用craft `hetong_redline.py inspect`实际返回的RL和唯一原文。不得把OCR图片文字当作可选择文本，或将P/T、Word内部批注号当RL。原稿未出现的新增条款，锚在最相关承接条款并说明插入位置。

引擎拒绝重叠既有批注、历史修订或其他复杂结构时，先按[Word工具边界](../../hetong-word/references/word-operation-paths.md)评估安全路径，不接受历史、不删批注、不改锚到无关文首强行通过。无法完成的具体批注应列出准确缺口；不得把只有报告的结果称为双交付已完成。

## 数据与命令

在原报告JSON基础上增加`bundle`及`issues`：

```json
{
  "bundle": {
    "source": "原件/已核验基线.docx",
    "source_sha256": "填写实际64位SHA256",
    "author": "合同审阅",
    "report_name": "某合同_v1_XQY审核报告.docx",
    "comments_name": "某合同_v1_XQY批注稿.docx"
  },
  "issues": [{
    "id": "R-001",
    "section": 2,
    "type": "revise",
    "title": "开票责任",
    "location": "第X条开票条款",
    "original_excerpt": "经核对的原文，可选",
    "detail": "本方的具体风险和依据。",
    "suggestion": "建议替换为：完整建议文字，未确认参数写【待确认：……】。",
    "comment_summary": "需要修改的简短原因和方向。",
    "anchors": [{"para": "RL0002", "text": "该段内唯一的实际锚文本"}]
  }]
}
```

`section`为1—8或`extra`；固定条款匹配可放在事项自己的`fixed_clauses`。JSON仍需其他基本报告字段，不把上面节选当成完整可运行示例。源路径相对该JSON；文件名不得含目录。

`build_bundle.py --input 数据.json --out-dir 交付_v1 --dry-run`不写文件；正式生成先在临时目录构建、核验，再发布完整的新交付目录。目录中只有两份业务DOCX，其余放`核验/`，包括报告Markdown、冻结数据、批注计划和双向映射。已有目录拒绝覆盖。

无R事项时显式传空数组：输出原样副本并说明新增批注为零，不伪造提醒。每个应批事项缺少合法锚点则预演失败，不静默漏掉。`--verify 交付目录`复查源指纹、双方文件、建议全文及原生批注结构。生成器技术核验通过不证明语义判断、法律结论或Word/WPS界面显示已通过。

## 明确纠错输入

`type: "correction"` 必须给出 `correction_basis`（`typo`、`grammar`、`plain_logic`、`verified_rule`、`bilingual_alignment`），每个锚点提供准确 `text` 和 `replacement`。`verified_rule`另提供已核验的`verified_basis`；`bilingual_alignment`另提供最终`chinese_source`，中文与英文的必要修改一并列入锚点。空replacement表示删除。一般商业建议继续用revise，不得伪装为correction。

本次明确只批注时在bundle设置`comments_only: true`，生成器拒绝correction。完整授权边界、短批注和两页简报见[统一规则](../../hetong-word/references/review-rules.md)。
